## 二、缺陷明细

### H-1（高·数据串号/删除不彻底）wipe 不清理本机年级归档
- 位置：`web/src/core/storage.ts:135-141`（`clearLocalData` 只 remove `CACHE_KEY`、`PIN_KEY`）；`web/src/core/gradeArchive.ts:17`（`KEY='xiaotao-grade-archives-v1'`，**全局键、不分家庭**）；对照 `web/src/app/AppProvider.tsx`（a5afc1c 提交的 wipe 分支：`clearOutbox()` + `clearLocalData()` + 内存重置，无归档清理）。
- 证据链：①本机归档由未登录切换通道写入（AppProvider.tsx:680 `saveGradeArchive(fromKey, slice)`，切片含 lessons/pointers/mistakes/weakness/dictationQueue 全量学习数据）；②归档恢复在未登录通道同样触发（AppProvider.tsx:681 `takeGradeArchive(toKey)`）；③a5afc1c 的 accountSwitch 测试（web/tests/accountSwitch.test.ts）断言的键只有 cache/device/outbox/account 四类，**不含 grade 归档键**，测试无法暴露该缺口。
- 影响：家庭 A 退出选「清空本机数据」后，A 的年级归档仍留在 localStorage。家庭 B 在同机绑定（或访客模式）后走未登录切换通道切到 A 曾归档的同一年级学期（如都是 g2s2）时，B 直接恢复出 A 孩子的学习进度与错题——**跨家庭数据泄露**；同时「清空本机数据」承诺未兑现（A 的数据残留）。这正是 a5afc1c 提交信息自述要防的"跨家庭数据串号"，现有实现留了这条旁路。
- 修复方向（供参考）：wipe 时一并移除 grade 归档键；或归档键按家庭/账号维度隔离。

### H-2（高·条件性数据丢失）服务端切年级：删档先于 CAS
- 位置：`server/src/services/gradeService.ts:159`（`if (restored) await …gradeArchives.delete(familyId, toKey)`）→ `:167-171`（`casUpdate(baseRevision=row.revision)`，未命中 `throw new AppError('revision_conflict')`）。仓储层无事务包裹（`server/src/repos/prisma.ts` 仅 `createWithFamily` 用 `$transaction`；内存仓储同理，逐条 await）。
- 场景：双设备同家庭。设备 A 切年级：读取 state（rev N）→ 恢复 toKey 存档 → **删除该存档** → CAS 落库。若此刻设备 B 已推送（rev N+1），CAS 失败 409，客户端提示"切换没有完成"（SettingsPage `confirmGradeSwitch` catch 分支）；家长重试切换时 toKey 存档已被删除 → `restored=false` → **目标年级进度静默清零**（fromKey 侧会重新封存，损失的是"切过去那个年级"的存档）。
- 触发条件：读-CAS 窗口内的并发写（客户端 800ms 防抖自动推送+60s tick，窗口小但真实存在）。
- 修复方向：CAS 成功后再删档（或仓储层单事务）。附带同函数两处较小问题见 L-2。

### M-1（中·功能错误）历史年级列表过滤条件写错
- 位置：`web/src/pages/RecordsPage.tsx:114`：`return !(grade === (state.grade ?? 2) && (override ?? semester) === semester);`
- 问题：意图是隐藏"当前生效年级+学期"的存档。但 `override ?? semester` 在未设置学期覆盖（默认态）时恒等于 `semester`，比较恒真 → **当前年级下所有学期的存档全部隐藏**，包括并非生效学期的那一册（应为 `override ?? autoSemester()`）。设置过学期覆盖时行为才正确。
- 影响：默认配置下，历史年级列表漏显存档，无法查看/导出（数据仍在，仅展示错误）。

### M-2（中·功能错误）未登录通道 switchGrade 不标记 dirty
- 位置：`web/src/app/AppProvider.tsx:659-691`（本机通道：封存→恢复→`setPack`→`dispatch replace`→`saveCachedState`→notify 后 return，**无 `markDirty()`/`schedulePush()`**；对照 `importData`、`prepareCurrent` 等其他改 state 路径均标记）。
- 影响：①本机切换（改了 lessons/pointers/grade 等同步字段）不进入推送队列，在其他设备/云端看来年级未变，直到该设备发生任意其他动作才随携带推出；②若期间云端 revision 被其他设备推进，`pullOnce` 会 adopt 云端旧年级状态，**本机切换被回滚**，且 `takeGradeArchive` 已按"单副本"语义消费掉存档，进度无法再次恢复。
- 修复方向：本机通道补 `markDirty()+schedulePush()`（或显式决定切换态不上云的口径并同步给多设备语义）。

### M-3（中·功能逻辑错误）运动星星可重复刷
- 位置：`web/src/core/sports.ts:98-102`（`metBefore = wasMet ? sportsMetCount-1 : sportsMetCount; starGain = justMet && metBefore < 3 ? 1 : 0`）；结算入口 `web/src/core/state.ts:255-270`（reducer 直接累加 `delta.starGain`）。
- 复现：同日同一项目，先达标（+1 星）→ 改数值跌破达标线（"只增不扣"不回收）→ 再改回达标：此时 `wasMet=false`、`justMet=true`，`metBefore` 因该项目当前未达标而不计入 → `0 < 3` → **再 +1 星**。反复横跳可无限获取星星（每日上限只统计"当前达标项数"，未记录"当日已发放星数"），商城星币经济被绕过；`sportsDayStatus.starEarned`（sports.ts:73 推导展示）与实发数也会不一致。
- 注：web/tests/sports.test.ts 21 例未覆盖"跌破再达标"场景。修复方向：SportsState 增加当日已发星计数（或按 date 键记录）。

### L-1（低·规范/注释失实）grade 路由无限速
- `server/src/routes/grade.ts:4` 注释称"限速沿用…独立窗口（30 次/分钟）"，但 `server/src/app.ts:155-156` rate-limit 插件 `global:false`，仅显式声明 `config.rateLimit` 的路由生效；grade 两条路由（routes/grade.ts:44-60、63-65）均未声明 → 实际不限速。鉴权后风险有限，建议补配置或改注释。

### L-2（低·死条件/坏味道）archiveSummary 恒假表达式
- `server/src/services/gradeService.ts:51-57`：`filter((m) => isRecord(m) && !isRecord(m) ? true : !(m as {resolvedAt?}).resolvedAt)` —— `isRecord(m) && !isRecord(m)` 恒假，等价于直接取 `!resolvedAt`。net 效果碰巧正确（统计未订正数），但表达式失去意义且误导审阅。

### L-3（低·体验）运动页静默/假成功反馈
- `web/src/pages/SportsPage.tsx:94`（`if (!delta) return;`）：数值与已记录值相同再点「更新记录」完全无反馈；`:108-120` submitCustom：同名/同 id（`Date.now().toString(36)` 同毫秒碰撞）被 reducer 幂等丢弃（state.ts:296-303）时，页面仍提示「…加好了」。

### L-4（低·隐患）reducer 非纯 + dispatchLocal 双重归约
- `web/src/core/state.ts` 多处 `new Date().toISOString()`、praise-add 用 `Date.now()` 生成 id（约 :227）；`AppProvider.tsx:485-490` `dispatchLocal` 先 `dispatch(action)` 再同步 `appReducer(stateRef.current, action)` —— 同一 action 被计算两次，时间戳/id 不同 → `stateRef`（推送快照用）与 React state（渲染与缓存用）在 `updatedAt`、praise id 上漂移；StrictMode 下 reducer 双调用进一步放大。当前用户可见影响趋近于零（内容相同、id/时间戳不同），属正确性隐患，建议 reducer 纯化、时间戳在 action 携带。

### L-5（低·口径）连续打卡显示过期
- `state.sports.streak` 仅在当日首次打卡时推进（sports.ts:94-113）；跨天未打卡时 SportsPage/TodayPage/RecordsPage（如 `state.sports.streak` 直接渲染）仍显示旧值，直到下次打卡才重置为 1。展示口径问题，非数据损坏。

### L-6（低·错误处理）wipe 退出无错误反馈 + 在途推送竞态
- `SettingsPage.tsx` `handleLogout`（约 :236-248）无 catch：`logoutRequest()` 失败（离线）时弹窗停留、无任何提示；`parentLogout('wipe')` 清理后，若有在途 `pushNow`，其成功回调仍会 `updateDevice({revision:…})` 把旧家庭 revision 写回新设备态，后续首次推送可能吃一次 409（可经冲突弹窗恢复）。建议 handleLogout 捕获并提示；wipe 时置 push 失效哨兵。
