## 一、测试分层体系（L1–L6）

| 层级 | 名称 | 运行载体 | 职责 | 准入规则（什么必须/只能放这层） |
|---|---|---|---|---|
| L1 | 纯函数单元 | `npm run test`（Vitest，`vite.config.ts` 当前 `environment: 'node'`） | `src/core/`、`src/data/` 全部纯函数：计划生成、判分、进度、口算、PIN、同步决策（`decideBootstrap`）、备份解析、归档/迁移等新纯逻辑 | 不触碰 DOM、fetch、定时器真实时间、localStorage；输入输出可 JSON 序列化。任何新业务纯函数（归档、迁移、商店、计时、token）**必须**先落此层 |
| L2 | jsdom 组件 | Vitest + Testing Library（文件头 `// @vitest-environment jsdom`，因全局环境是 node） | `src/pages/`、`src/features/`、`src/components/` 组件渲染与交互：按钮降级态、表单校验、对话框行为、隐私页文案 | 不发真实网络；`useApp`/`AppProvider` 以注入 state + spy dispatch 方式测；浏览器 API（`speechSynthesis`、`sessionStorage`）用 jsdom 缺省或手动 stub。**当前此层为 0 例，是首要补强对象** |
| L3 | API 集成测试 | `npm run test:server`（supertest 直挂 Fastify 实例 + 测试专用 PostgreSQL；scripts 随 `server/` 开发落地，先写进 4.1 门禁标准） | `server/src/` 全部路由的集成行为：认证三接口（注册/登录/刷新）、状态两接口的校验、CAS、错误码（400/401/404/405/409/413/415/429/503 及 `token_expired`/`archive_wiped`）、健康检查、审计接口 | 真实 SQL 语义（唯一键/事务/JSONB）首次进入自动化覆盖；测试库与用例隔离——每个用例事务回滚或重建（truncate）`family_state` 等六表，零残留；凡改 API 契约（新字段、新限制、新错误码、新路由的鉴权/限速结论）必须同步扩例 |
| L4 | Playwright GUI | `mockups/.tools/accept-*.mjs`（390×844 为主视口，跑 `npm run preview`；需后端的场景用 `npm run dev` 由 vite 代理 `/api` → 本地 api，或不起后端——离线优先机制下同步横幅呈离线/未登录态属预期，07 §10.3。v1 的 `dev/function-preview.mjs` 假函数预览随平台方案退役） | 端到端用户流：引导、答题、家长区、冲突弹窗、备份导入、商店兑换、只读周报链接 | 覆盖"多条纯函数串联 + 真实渲染"的路径；每次发布前全量跑，证据写 `screenshots/acceptance/`。它不做像素对比，只做行为与 DOM 断言 + 截图 |
| L5 | 视觉验收 | 同 L4 脚本的截图产物（`app-shots.mjs`、`flat-shots.mjs`、`diag-overflow*.mjs`） | 关键页面在 320 / 390 / 430 / 844 桌面档位的布局不溢出、不截断；图标/manifest 存在 | CSS 与布局类缺陷（如 P1-01）在此层闭环；改版式必须三档视口（当前只测过 390） |
| L6 | 真机 | 家长的 iPhone（iOS Safari）与 Android 手机（Chrome），真实云端站点 | TTS 语音行为、PWA 安装与提醒、真实双设备同步与 409 三场景 | 唯一无法自动化的层；证据必须录屏 + 截图留档（见第五节清单）。凡 L6 发现的问题，能在 L1/L2 复现的部分必须下沉成自动化用例 |

分层原则：**用例尽量下沉**。能在 L1 断言的逻辑不放到 L2，能在 L2 断言的交互不放到 L4；L4/L5/L6 每条用例必须指向至少一个无法在下层验证的理由（真实渲染、真实浏览器 API、真实设备/网络）。

**L3 测试库的本地起法（二选一，02 §8.1/§4.3-4）**：① `docker compose -f server/docker-compose.test.yml up -d` 一键起测试专用 PostgreSQL（库名 `xiaotao_test`）；② 开发机已装 PostgreSQL 时本地建同名空库（`DATABASE_URL` 指向它）。测试套件 `beforeAll` 跑 `prisma migrate deploy`、`afterEach` truncate 六表，用例间零残留。**旧假库去留**：`dev/fake-db.mjs`、`dev/function-test.mjs`、`dev/function-preview.mjs` 随 v1 平台方案退役删除（02 §8.4、07 §10.3，git 历史可考）；退役前置条件＝server 侧映射用例（约 47 例，见 2.2）全绿，并在同一退役 PR 中移除 `check:function`/`test:function`/`preview:function` 三条 npm scripts。

### 3.11 风险专项：归档升级窗口的「旧客户端抹档」（架构师评审）

**风险描述**：P0-① 上线后，云端已存含 `archive` 摘要的状态；此时若某台**未升级**的旧客户端用它自己那份（无 `archive` 字段的）完整状态**成功执行一次 CAS 推送**，云端 `archive` 摘要会被整份覆盖抹掉，而被压缩的明细早已丢弃、不可重建——**数据永久丢失**（纯客户端行为，与后端平台无关，v2 下风险不变，02 §6.4）。防护采用双保险：服务端门槛（v2 已钉死为 PUT 校验链第 6 条——云端 `archive` 非空而请求缺失该字段 → **400 `archive_wiped`**，02 §3.2/§6.4，不再是「提升 schemaVersion 或保档合并二选一」）＋ 发布门禁（4.2 第 7 条「全设备同批升级」，即 07 §4 E2 硬闸门）。

## 四、回归门禁定义

### 4.1 合入标准（每个 PR / 每次向主干合并）

1. `npm run build` 通过（含 `tsc --noEmit` 类型检查）。
2. `npm run test` 全绿，且用例总数 ≥ 当前基线 63（只增不减；删用例必须在 PR 说明中给出理由并经测试工程师确认）。
3. `npm run check:server`（prisma validate + server 侧 `tsc --noEmit` + lint）与 `npm run test:server`（supertest + 测试库）全绿——两条 scripts 随 `server/` 开发落地，**先写进本标准**；落地前旧命令 `check:function`/`test:function` 仍按 31 例基线（2026-10-25 实测）运行，`server/` 首个可运行 PR 起切换（02 §8.4）。server 侧用例基线约 47 例（2.2/3.12），只增不减；删用例必须在 PR 说明中给出理由并经测试工程师确认。
4. 改 `server/prisma/schema.prisma` 的提交必须包含 `server/prisma/migrations/` 下的迁移文件（02 §4.3、07 §4 A6 门槛）。
5. **新增/变更行为至少附带 1 条自动化回归用例**（落第三节指定的文件）；修复 P0/P1 级缺陷的 PR 必须引用缺陷编号（如 `P1-02`），并满足下述复验要求。
6. 涉及 UI 的缺陷至少 1 张截图证据；涉及 CSS 布局的（P1-01 类）必须 320/390/430 三档视口截图。
7. PR 描述列出：变更点、新增用例 ID、证据路径（按第七节命名规则）。

### 4.2 发布标准（对外发布 / 家长真机使用）

1. 合入标准全部满足，且主干最近一次全量运行四条命令全绿（`npm run build` / `npm run test` / `check:server` / `test:server`，与 07 §4 A2 同口径；`server/` 落地前暂以 `check:function`/`test:function` 顶替后两条）。
2. `mockups/.tools/` 下全部 `accept-*` 验收脚本通过，证据落 `screenshots/acceptance/` 且命名符合第七节约定。
3. 真机验证清单（第五节）当期完成：双平台 TTS + PWA + 真实双设备 409 三场景，全部有录屏/截图证据。
4. 线上冒烟全绿：按 07 §5.9 curl 清单逐条执行并留档——健康检查（D1）、鉴权墙 401（D2）、注册（D3）、登录（D4）、空态读取（D5）、首写 PUT（D6）、409 复现（D7）、登录限速 429（D8）、静态资源与缓存策略（D9–D10）、日志 redact（D11）、双设备三场景（D12）、真机绑定（D13）；归档发布另含 D14（archive_wiped 防线）。此项取代 v1 的「Deno 类型检查」（STATUS 第六节第 3–4 条中平台专属项作废，实测部分由本条承接）。
5. 缺陷状态：无未修复 P0/P1；P2 遗留须列入「已知问题清单」并经家长确认可接受。
6. `docs/STATUS.md` 与本文档第七节验收矩阵同步更新（需求 → 用例 → 证据三列对齐）。
7. **归档结构变更专项门禁（全设备同批升级）**：凡触碰 `dailyPlans`/`dailyLogs` 结构或 `schemaVersion` 的发布，须同时满足——① RISK-01/02 **server 侧用例**全绿（3.11，落点 `server/test/state.test.ts`）；② 家庭全部登记设备逐台确认已升级到同一版本，检查单留档 `docs/acceptance/release-<日期>-devices.md`（＝07 §4 E2 硬闸门，其前置 E1「首归档前自动备份落袋」须同步完成）；③ 发布后 48 小时监控 413/400（`archive_wiped`）与 revision 回退异常（衔接 07 §8.4 周检第 10 项）。三者任一未完成，**不得发布归档版本**（对应 3.11 风险）。
8. 发布全流程按 07 §4 五组发布检查单执行并全部勾满：**A 上线前·代码侧**（A1–A9）、**B 服务器侧**（B1–B8）、**C 数据库侧**（C1–C5）、**D 上线后冒烟**（D1–D14）、**E 硬闸门**（E1–E3）；未勾项须书面豁免并随 E3 会签留档。本节第 1–4 条与 A2/A3/D 组为同一批证据，不重复执行。

## 五、真机验证清单（L6）

### 5.1 iOS Safari TTS（听写朗读 + 读题按钮）

### 5.3 真实双设备 409 三场景

设备 A（平板）与设备 B（手机）登录同一账号，均完成引导。

| 场景 | 步骤 | 通过标准 |
|---|---|---|
| ① 离线完成 | A 开飞行模式 → 完成一个任务（得星）→ 恢复网络等待推送 → B 此前已推送过更新 | A 恢复后推送触发 409 时弹 ConflictDialog（P1-02 修复后的儿童友好文案、逐项对比、二次确认、「稍后处理」可选）；选「保留这台平板」后 A 数据上云，B 再打开可见 |
| ② 同修订号重开 | A、B 同为 revision N 且 A 有 dirty 改动 → 关闭 A 再重开 | 不弹假冲突（`decideBootstrap` 判 keep-local），A 的改动自动补推；B 刷新后可见，revision 恰 +1 |

### 6.1 严重级别与修复时限
