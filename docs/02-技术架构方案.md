## 一、架构决策记录

### ADR-001：脱离 Qoder 平台，改为主流自托管架构

- **状态**：已裁定并生效（PM，2026-10-24 决策；本文为落地详细设计）。
- **背景**：v1 架构深度绑定 Qoder 平台——身份由平台网关注入的 `x-qoder-user-context` 头提供（函数只读不自校验，docs/ARCHITECTURE.md:121）、计算层为平台 Deno Edge Function（`functions/handler.mjs`）、静态站与云资源均未创建（docs/ARCHITECTURE.md:141）、本地验证只能靠假库与假身份头（`dev/function-test.mjs`，不代表真实平台行为，docs/ARCHITECTURE.md:135）。平台锁定导致数据不自主、真实环境不可测、部署链路不可控。
- **决策**：彻底脱离 Qoder 专属架构，改为主流自托管：Node.js 20 LTS + Fastify 自建 API、PostgreSQL 16 + Prisma 自管数据、Docker Compose + nginx 单机部署、自建账号体系（argon2id + JWT）。
- **被替换项对照表**：

| 能力 | v1（Qoder 平台绑定） | v2（主流自托管） | 迁移性质 |
|---|---|---|---|
| 身份鉴权 | 平台网关注入并验证 `x-qoder-user-context` 头，函数只读不自行校验（docs/ARCHITECTURE.md:121）；无账号体系 | **自建账号体系**：家长注册（用户名+密码，argon2id 哈希），登录发 JWT access（约 2h）+ refresh token（约 30 天，入库可吊销/轮换） | 重写 |
| 计算层 | Deno Edge Function（`functions/handler.mjs` 单 handler） | **Node.js 20 LTS + TypeScript + Fastify**，`server/` 内 routes → services → repositories 三层；Zod 请求校验；pino 结构化日志 | 重写（CAS 语义逐条平移，见第三章） |
| 托管 | Qoder Sites 托管 dist（未创建） | **Docker Compose**：nginx 容器托管 dist 静态文件并反代 `/api` → `node:api` 容器；postgres 数据卷；HTTPS 由 nginx + Let's Encrypt | 重写 |
| 数据访问 | 匿名 key 经 Supabase REST（`functions/adapter.mjs`） | **Prisma 直连 PostgreSQL**（`DATABASE_URL` 环境变量，仅 compose 内网） | 重写 |
| 数据库 | Supabase Postgres 单行 `family_state`（id='family'） | 自托管 PostgreSQL 16 **六表 schema**（第四章） | 重新设计（单行 CAS 语义保留） |
| 同步端点 | `GET/POST /functions/v1/app?action=state`，`credentials: 'same-origin'` 携平台登录态（`src/core/sync.ts:96,111,82`） | `GET/PUT /api/v1/state`，`Authorization: Bearer <accessToken>` | 端点与鉴权头替换，**语义平移不推翻**（前端已验证的 dirty/409/防抖体系不动） |
| 前端 | React 18 + TS + Vite SPA | **不动**（HashRouter、离线优先、Context+useReducer 状态树、`src/core` 纯函数纪律全部保留；仅改 `sync.ts` 端点/鉴权头/401 处理与 AppProvider 登录态编排，见第五章） | 最小改动 |

- **后果（正面）**：数据与服务完全自主；真实 HTTP + 真实数据库可测（supertest + 测试库，见第八章）；无平台级锁定，家庭 VPS/NAS 单机即可部署。
- **后果（义务）**：v1 依赖平台的三道前提——网关可信身份、平台入口的 TLS 与限流、站点私有访问控制（docs/ARCHITECTURE.md:121）——**全部消失，安全责任自担**，必须按 2.3 红线自行补齐。
- **明确排除**（复杂度封顶）：不引入微服务、Kubernetes、消息队列、多实例横向扩展、CDN。目标形态就是「一台家庭服务器 + `docker compose up -d`」。

### 2.2 信任边界说明（与 v1 的关键差异）

v1 隐含「平台网关可信」前提：身份由网关注入并验证、函数运行在平台不可绕过的入口之后、数据库隔离依赖站点私有访问控制而非行级策略（docs/ARCHITECTURE.md:121 明言这是确认过的边界）。**v2 中该前提不复存在**，重新划界如下：

1. **公网可信边界止于 nginx**。只有 80/443 暴露；`node:api` 与 `postgres` 仅在 compose 内网可达，postgres 的 5432 不做端口映射。TLS 由 nginx + Let's Encrypt 统一终止，API 与数据库之间无需再加密。
2. **API 成为唯一业务入口，必须自我防卫**。v1 里「上游已验证身份」的假设作废：JWT 校验、限速、body 校验全部在 Fastify 内完成；身份（`familyId`）只从 token claims 取，**绝不从请求体取**——这条原则平移自 v1（`functions/handler.mjs:193-198` 注释：caller 已解析可信用户，handler 永不信 body 里的身份），只是「可信来源」从网关头换成了 JWT 签名。
3. **浏览器整体不可信**。与 v1 相同：服务端只校验信封（`schemaVersion === 1`、体积、鉴权），不深验业务字段，读侧权威仍是前端 `normalizeState()`（`src/core/model.ts:282-401`）。v2 新增不可信面是 **token 本身可能被盗**，因此 access 短时效（2h）、refresh 可吊销且轮换、复用检测三重约束（3.1）。
4. **secret 只存在于 server 容器环境变量与部署机 `.env`**。跨边界介质（日志、响应体、前端 dist 产物、备份 JSON 文件）一律不得出现 secret（2.3 红线 2；备份文件格式 `src/core/storage.ts:137-148` 不含任何 token，保持不变）。

### 2.3 自托管安全红线（责任自担，违反任一条不得发布）

v1 交给平台的三件事（限流、TLS、访问控制），v2 必须自己扛。以下为**一票否决红线**，与 03 号文档第八节配套：

1. **限速红线**：`/api/v1/auth/login` 与 `/api/v1/auth/register` 必须限速——登录 **5 次 / 15 分钟，键 = IP + username**（`@fastify/rate-limit` 自定义 keyGenerator），超限 429 `rate_limited`；`/api/v1/state` PUT 挂宽松限速（建议 60 次/分钟/账号）防误刷打爆单机数据库；`/api/v1/auth/refresh` 限速（建议 30 次/分钟/IP）。**新增任何路由，merge 前必须回答「要不要鉴权、要不要限速」并写入路由表注释**。
2. **secret 管理红线**：`JWT_SECRET`（≥32 字节随机）、`DATABASE_URL`、（P1 预留）VAPID 私钥——不入 git 仓库（仓库只提交 `.env.example` 键名）、不写入 Docker 镜像层、不进入前端 dist 产物、不出现在 pino 日志（启动时配置 redact `authorization`/`cookie`/`set-cookie`）。怀疑泄露即全量轮换（JWT_SECRET 轮换的代价是所有 access 立即失效、refresh 不受影响，可接受）。
3. **HTTPS 红线**：nginx 强制 TLS；80 端口仅保留 ACME challenge 与 301 跳转；任何 API 不得经明文 HTTP 可达。refresh cookie 必须 `Secure` 属性（生产环境 refresh 仅在 HTTPS 下会被浏览器存发，这是期望行为）。
4. **凭据存储红线**：密码只存 argon2id 哈希（参数固化为 `server/src/lib/argon2.ts` 常量，升级参数须支持旧哈希就地重哈希）；明文密码与哈希永不落日志；refresh token 库内只存 SHA-256 哈希（`refresh_tokens.token_hash`），原始值只存在于 cookie 传输中。
5. **数据库暴露红线**：postgres 端口不对公网映射；`prisma db push` 禁止用于生产（只允许 `prisma migrate deploy`）；备份/恢复与数据卷策略见 docs/07-部署与运维方案.md。

## 三、API 契约草案（/api/v1）

**总则**：REST 风格、`/api/v1` 前缀、JSON；错误体统一 `{ error: { code, message } }`（`message` 为面向用户的中文短句，**不含堆栈/SQL/内部路径等细节**——沿袭 v1「503 无 message 泄漏」的既有用例断言，`dev/function-test.mjs:262-265`）；状态类接口一律 `cache-control: no-store`（语义平移自 `functions/handler.mjs:5-9`）；成功体沿用 v1 的 `{ ok: true, ... }` 信封——这是刻意决定，使 `src/core/sync.ts` 的 payload 解析（`sync.ts:39-51,61-75`）除端点/方法/鉴权头外零改动。

**设备绑定模型**：孩子平板首次使用时由家长在该设备上登录一次（输入家长账号密码）完成「绑定」；此后该设备凭 httpOnly refresh cookie 静默续期 access token，无需再人工登录。绑定动作自 2026-10-25 起内置在首次引导第 1 步（docs/06 §3.10），家长不再需要事后进设置页登录。设备不注册、无设备账号，服务端只认 `account` 与 `family`。PIN 门禁仍是**纯客户端机制**（`src/core/pin.ts`、设备态 `src/core/storage.ts:4-12`，PIN 哈希留在 localStorage 不上云）。

### 3.1 认证三接口

#### (1) POST /api/v1/auth/register —— 注册（创建家庭 + 账号）

限速：3 次/小时/IP（防批量注册）。

```json
// 请求
{ "username": "taomom", "password": "zht-2008-xiaotao" }
// 201 响应
{
  "ok": true,
  "account": { "id": "cktr…", "username": "taomom" },
  "familyId": "ckts…",
  "accessToken": "eyJhbGciOiJIUzI1NiIs…"
}
// Set-Cookie: xiaotao_refresh=<256-bit随机串>; Path=/api/v1/auth; HttpOnly;
//             Secure; SameSite=Strict; Max-Age=2592000
```

规则：`username` 3–32 位、字符集 `[a-z0-9_-]`（服务端小写化后 unique）；`password` 8–128 位任意可见字符。注册事务内创建 `families` 行 + `accounts` 行（argon2id 哈希）并发放首对 token。`family_state` 行**不**在此创建——沿用 v1 惰性建行语义（首次 `PUT baseRevision=0` 时插入，`functions/handler.mjs:219-225`）。多家长共管一个家庭（第二个账号加入既有 family）本期不做，触发条件见第七章演进预留。

#### (2) POST /api/v1/auth/login —— 登录

限速：**5 次 / 15 分钟，键 = IP + username**（红线 2.3-1）。

```json
// 请求
{ "username": "taomom", "password": "zht-2008-xiaotao" }
// 200 响应：同 register（account / familyId / accessToken + Set-Cookie refresh）
// 错误
// 401 { "ok": false, "error": { "code": "invalid_credentials", "message": "用户名或密码不正确" } }
// 429 { "ok": false, "error": { "code": "rate_limited", "message": "尝试过于频繁，请15分钟后再试" } }
```

规则：用户不存在与密码错误返回**同一** `invalid_credentials`（不泄露账号存在性）；argon2id 校验恒定耗时。登录成功即签发 access + 新 refresh（每次登录都生成新 refresh，旧 refresh 不吊销——多设备并存是预期场景）。

#### (3) POST /api/v1/auth/refresh —— 静默续期（token 轮换）

限速：30 次/分钟/IP。请求无 body，凭 httpOnly refresh cookie。

```json
// 200 响应
{ "ok": true, "familyId": "ckts…", "accessToken": "eyJ…" }
// Set-Cookie: xiaotao_refresh=<新随机串>; …（旧 token 同时置 revoked_at）
// 401 { "error": { "code": "invalid_refresh", … } }   // 未知/过期/已吊销 → 同时清 cookie
// 401 { "error": { "code": "refresh_reused", … } }    // 已轮换 token 复用 → 视为泄漏
```

**轮换与复用检测**：每次 refresh 成功即吊销旧 token、发放新 token（30 天滚动续期，孩子设备长期免登录）；若收到已吊销（已轮换）的 token，判定泄漏：吊销该账号**全部** refresh token、写 `security_events`（type `refresh-reuse`），客户端收到 `refresh_reused` 须整体重新登录。这是 refresh token「可吊销/轮换」要求（`refresh_tokens` 表存在的意义）的核心场景。

#### token 规格表

| token | 形态 | 时效 | 客户端存储 | 服务端吊销 |
|---|---|---|---|---|
| access | JWT HS256，claims `{ sub: accountId, fid: familyId, typ: "access", iat, exp }` | 2h | **仅内存**（不落任何 storage） | 不可（短时效自灭） |
| refresh | 256-bit crypto 随机串（opaque，非 JWT） | 30 天 | httpOnly cookie（见上） | 可（`revoked_at`，逐条与全量） |

`JWT_SECRET` 见红线 2.3-2。`typ` 声明防止 token 混用（未来 share token 同款纪律，见 7.10）。

### 3.2 状态两接口（CAS 语义平移）

#### GET /api/v1/state

`Authorization: Bearer <accessToken>`。响应 200（`cache-control: no-store`）：

```json
// 有数据
{ "ok": true, "data": { /* SyncState */ }, "revision": 42, "updatedAt": "2026-10-25T12:00:00Z" }
// 无数据（家庭首次使用）
{ "ok": true, "data": null, "revision": 0 }
```

语义与 v1 GET 完全一致（`functions/handler.mjs:206-211`）：无行返回 `{ data: null, revision: 0 }`；只投影 `data/revision/updated_at`，不做白名单外返回。行选择键从 v1 的固定 `id='family'` 变为 `family_id = token.fid`。

#### PUT /api/v1/state

`Authorization: Bearer`；body `{ "data": SyncState, "baseRevision": number }`。校验链（每条都平移自 v1 `parseWriteBody` / `handleState`，标注来源行号）：

1. `content-type` 非 `application/json` → **415 `unsupported_media_type`**（`functions/handler.mjs:148-150`）。
2. 体积双保险：`content-length` 预检 + 请求体流式累计，任一超过 **256KB** → **413 `payload_too_large`**（`functions/handler.mjs:3,152-163`）。Fastify 侧落为该路由 `bodyLimit: 256 * 1024` + 手工 content-length 预检；认证类路由另设 `bodyLimit: 4KB`。
3. JSON 解析失败 / body 非对象 → **400 `invalid_body`**（`functions/handler.mjs:166-174`）。
4. `data` 缺失、非对象、或 `schemaVersion !== 1` → **400 `invalid_body`**（`functions/handler.mjs:176-179`）。服务端**只**校验信封，不深验业务字段（设计硬约束 ④）。
5. `baseRevision` 非安全整数或为负 → **400 `invalid_body`**（`functions/handler.mjs:181-188`）。
6. **【v2 新增，RISK-01 服务端防线】** 云端行 `data.archive` 非空而请求 `data.archive` 缺失 → **400 `archive_wiped`**。把 v1「旧客户端一次成功 CAS 推送静默抹掉归档摘要且不可重建」（docs/00:66 RISK-01）从不可见变成显式失败 + 可监控。v1 刻意保持云函数零改动（v1 方案 2.7 节），自托管后无此包袱，补上这道防线；上线归档版本前该规则空转（云端无 archive 时永不触发），无兼容成本。
7. `familyId` 一律取自 token claims，绝不取自 body（原则平移自 `functions/handler.mjs:193-198`）。

CAS 写入流程（平移 `functions/handler.mjs:216-241`）：

- **无行**：`baseRevision !== 0` → 409 + 云端最新；`=== 0` → 插入 `revision = 1`；插入撞唯一键（并发抢先）→ 重读最新 → 409 + 最新（`functions/handler.mjs:219-225`）。
- **有行**：`updateMany({ where: { familyId, revision: baseRevision }, data: { data, revision: baseRevision + 1, updatedAt } })` 的**原子条件更新**，count === 0 即冲突 → 重读最新 → 409。等价于 v1 的 `.update().eq("revision", baseRevision)`（`functions/handler.mjs:84-101`），不引入「先读后写」竞态。
- 409 响应体（供前端 `ConflictError.remote` 消费，`src/core/sync.ts:121-129`）：

```json
{ "ok": false, "error": { "code": "revision_conflict" },
  "data": { /* 云端最新 SyncState */ }, "revision": 43, "updatedAt": "…" }
```

- 成功后**环形写历史槽位**（失败 try/catch 吞掉、不阻断主推送——v1 结论，见 6.3），再返回 200 `{ ok: true, data, revision, updatedAt }`。

### 3.3 GET /api/v1/health —— 健康检查

无鉴权、无缓存。200 `{ status: "ok", db: "ok", version: "<git sha>" }`；数据库不可达 → 503 `{ status: "degraded", db: "down" }`。用途：Docker healthcheck、nginx 探活、发布后人工验证。不得泄露内部拓扑（无连接串、无表名）。

### 3.4 辅助接口：审计上云（PIN 重置等）

v1 的安全事件只存 localStorage 最近 20 条（`src/core/storage.ts:77-106`）——换设备即丢、家长不可见。v2 落 `security_events` 表（第四章）：

- `POST /api/v1/security-events`：body `{ type, detail? }`，`type` 白名单（`pin-reset` / `content-migrated` / `refresh-reused`…与 04 号文档事件外显联动）；Bearer 鉴权 + 限速 10 次/分钟/账号；只写 token 所属 family。
- `GET /api/v1/security-events?limit=50`：家长区「安全记录」页数据源，倒序返回。
- 前端策略为**双写**：`recordSecurityEvent()` 本地照旧（离线可见），AppProvider 在线时 best-effort 上报，离线留存本地队列、恢复网络后补报——不因审计丢网络可用性。

## 四、数据库设计

### 4.1 Prisma schema 草案（`server/prisma/schema.prisma`，可直接使用）

```prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

model Family {
  id        String        @id @default(cuid())
  createdAt DateTime      @default(now()) @map("created_at")
  accounts     Account[]            // P0 每家庭 1 个；多家长共管为演进预留
  state        FamilyState?
  history      FamilyStateHistory[]
  securityLogs SecurityEvent[]

  @@map("families")
}

model Account {
  id           String   @id @default(cuid())
  username     String   @unique @db.VarChar(32)   // 已小写化；字符集 [a-z0-9_-]
  passwordHash String   @map("password_hash")     // argon2id，永不外发
  familyId     String   @map("family_id")
  family       Family   @relation(fields: [familyId], references: [id], onDelete: Cascade)
  createdAt    DateTime @default(now()) @map("created_at")
  refreshTokens RefreshToken[]

  @@index([familyId])
  @@map("accounts")
}

model FamilyState {
  familyId  String   @id @map("family_id")       // 每家庭一行：文档式单行 CAS
  family    Family   @relation(fields: [familyId], references: [id], onDelete: Cascade)
  data      Json                                  // SyncState 原文；DB 层不做 JSON Schema 约束
  revision  Int      @default(1)
  updatedAt DateTime @updatedAt @map("updated_at")

  @@map("family_state")
}

model FamilyStateHistory {
  familyId  String   @map("family_id")
  slot      Int                                     // 0..9 环形槽位 = revision % 10
  data      Json
  revision  Int
  updatedAt DateTime @map("updated_at")

  @@id([familyId, slot])
  @@index([familyId, revision])                     // 历史列表按 revision 倒序
  @@map("family_state_history")
}

model RefreshToken {
  id        String    @id @default(cuid())
  accountId String    @map("account_id")
  account   Account   @relation(fields: [accountId], references: [id], onDelete: Cascade)
  tokenHash String    @unique @map("token_hash")   // SHA-256(原始 token)；原始值不入库
  expiresAt DateTime  @map("expires_at")
  revokedAt DateTime? @map("revoked_at")           // 轮换/登出/泄漏吊销标记
  createdAt DateTime  @default(now()) @map("created_at")

  @@index([accountId])
  @@index([expiresAt])                              // 周期清理过期行
  @@map("refresh_tokens")
}

model SecurityEvent {
  id        String   @id @default(cuid())
  familyId  String   @map("family_id")
  type      String   @db.VarChar(32)                // 白名单：pin-reset / content-migrated / refresh-reuse / …
  detail    Json?                                     // 事件元数据；绝不存明文密钥/哈希
  createdAt DateTime @default(now()) @map("created_at")

  @@index([familyId, createdAt(sort: Desc)])
  @@map("security_events")
}
```

### 4.2 索引与约束说明

| 表 | 关键约束/索引 | 理由 |
|---|---|---|
| accounts | `username` unique；`@@index([familyId])` | 登录按用户名点查；按家庭找账号（预留多家长） |
| family_state | `familyId` 主键 | **每家庭一行**，单行文档式 CAS 的落点；无第二唯一键，`updateMany WHERE revision` 即 CAS |
| family_state_history | 复合主键 `(familyId, slot)`；`(familyId, revision)` 索引 | 环形 10 槽免 DELETE；历史列表只按元数据排序，避免全量拉 N×256KB |
| refresh_tokens | `tokenHash` unique（点查 + 天然防重复）；`(accountId)`（全量吊销）；`(expiresAt)`（清理任务扫描） | 轮换/复用检测/登出都靠点查 token_hash |
| security_events | `(familyId, createdAt desc)` | 家长区分页读审计流 |
| 全表 | `onDelete: Cascade` 自 family | 家庭删除即数据整体清除（P0 无删除入口，为合规预留） |

`data` 列为 JSONB 且**不设库级 JSON Schema**：状态语义权威在前端 `normalizeState()`（设计硬约束 ②④），库层只信 `schemaVersion === 1` 信封校验——与 v1「函数只投影三列、不做字段级白名单之外的事」（docs/ARCHITECTURE.md:103）一致。

### 4.3 迁移策略

1. **工具与命令**：本地 `prisma migrate dev --name <语义名>`（生成 SQL + client）；CI/部署 `prisma migrate deploy`（api 容器入口脚本中、应用监听之前执行）；**生产禁用 `prisma db push`**（红线 2.3-5）。迁移文件提交于 `server/prisma/migrations/`，与代码同 commit（03 号文档 3.4 门槛）。
2. **首版迁移**建齐六表与索引；`family_state_history` 槽位**不预插行**——首次写状态时 `upsert` 惰性建槽（v1 方案 4.2 的「10 槽预插入空行」是为绕开「平台不授予 delete」约束的自适应；自托管后无此约束，但环形 UPDATE 的写放大优势仍成立，方案保留、实现简化）。
3. **过期 refresh token 清理**：不引入定时任务框架——在 `/api/v1/auth/refresh` 成功路径上顺带 `deleteMany({ expiresAt < now - 7d })`（ opportunistic 清理），量级（家庭单机、个位数设备）完全够用。
4. **测试数据库**：`server/test` 使用独立 `DATABASE_URL`（如 `xiaotao_test` 库），`beforeAll` 跑 `migrate deploy`、`afterEach` truncate 六表——取代 v1 的 `dev/fake-db.mjs` 假库（真实 SQL 语义是 v2 测试的收益之一，见第八章）。
5. **备份**：postgres 数据卷 `pg_dump` 定时备份，恢复演练归 docs/07-部署与运维方案.md。

### 5.2 `src/app/AppProvider.tsx`（编排层，改动 6 处）

1. **启动序列前置静默续期**：`bootstrap()`（`AppProvider.tsx:260-303`）在 `fetchRemote()` 前先 `attemptRefresh()`（凭 cookie 换 access，孩子设备无感）；refresh 失败 → 进入「未登录」态：**本地缓存照常渲染、`ready` 正常置位**（离线优先不破坏），仅横幅提示「需要家长登录后才能同步」，且不发起推送。
2. **401 处理协议**：`pushNow`/`pullOnce` 的 catch（`AppProvider.tsx:210-229,250-253`）识别 `token_expired` → 刷新 token 后**重试一次**原请求（仅一次，防循环）；`login_required`/`refresh_reused` → 置 `SyncStatus` 新值 `'logged_out'`（**不是** `offline`——有网但未登录是不同事实），**不**走 `markDirty` 重试风暴（区别于 `AppProvider.tsx:217-221` 的 offline 分支）；本地 `dirty` 保持，家长重新登录后自动恢复推送。
3. **冲突/防抖/定时器全部不动**：800ms 防抖（`AppProvider.tsx:182-188`）、60 秒 ticker（`:319-330`）、`visibilitychange`/`online` 拉取（`:305-317`）、`resolveConflict` 对齐-再推（`:410-427`）——这是 PM 明确的「已验证体系不推翻」。
4. **新增 `src/app/auth.ts`**：register/login/refresh/logout 的 fetch 封装 + 内存 access token 存取 + 登出清理，与 `useSpeech.ts` 同层（浏览器 API 编排归 `src/app/`，03 号文档 1.3 纪律不变）。
5. **PIN 审计上云**：`resetPin`（`AppProvider.tsx:371-375`）在既有 `recordSecurityEvent('pin-reset')`（localStorage）之外 best-effort 上报 `security_events`（离线留存、恢复后补报）。
6. **首次绑定拉取（2026-10-25 增补，交互见 docs/06 §3.10）**：新增 `bindPull`/`bindLogin`/`bindRegister`——登录成功且本机未 onboarded 时立即 `fetchRemote()` 走一次 bootstrap 式 adopt（有数据 → `adoptRemote`，跳过昵称引导、只补本机 PIN；无数据 → 回称呼步）。它与第 2 条 `resumeSyncAfterLogin` 的区别：绑定时刻本地未 onboarded，**只拉不推**。兜底「先离线使用」路径不变——该路径完成后登录若撞上云端数据，冲突对话框是真实分歧下的正确语义。

### 5.3 token 存储位置建议（CSRF/XSS 权衡）

| 方案 | XSS | CSRF | 结论 |
|---|---|---|---|
| **A（推荐）**：refresh 放 httpOnly cookie（`Path=/api/v1/auth; Secure; SameSite=Strict`），access 只放内存 | httpOnly 对 JS 不可读，refresh 无法被脚本窃取；access 在内存，刷新页面即消失，被盗窗口 ≤2h | cookie 会被自动携带 → 但三重缓解：`SameSite=Strict` 拦截跨站携带；`Path` 限定只有 auth 路由收到；refresh 端点仅接受 `application/json`（跨站表单无法伪造该 content-type，且本服务不开放跨域 CORS） | **采纳** |
| B：全部放 localStorage | 任意脚本可读走 30 天 refresh → 账号整体沦陷；本项目虽零第三方脚本（依赖红线，03 号文档 5.4），但孩子平板浏览器内核老旧、注入面未知 | 免疫 | 不采纳 |

配套纪律：access token **绝不**写入 localStorage/sessionStorage/SyncState/备份文件（备份格式 `src/core/storage.ts:137-148` 不含 token，保持）；token 与学习数据完全隔离。同源部署（nginx 同域反代 `/api`）使方案 A 无任何跨域 cookie 复杂度。

### 5.4 离线行为不变声明

离线优先机制**零变化**：启动先渲染 localStorage 缓存 → 拉远端 → `decideBootstrap()` 纯函数决策（`src/core/syncBoot.ts:20-27`）；本地 `dirty` 标记与修订号、8 秒超时归一 `offline`、断网期间全部功能可用、恢复后自动推送——以上均不依赖鉴权成功。唯一新增分支是「**有网但未登录**」（`logged_out`）：本地数据可看可用，云端同步挂起待家长登录。

## 六、平移保留的方案（v1 结论核对仍成立）

以下四项为 v1 方案中架构无关的结论，逐条核对后平移；涉及 `functions/` 的引用已改为 `server/` 落点。

### 6.1 状态归档三档窗口与 256KB 预算（FR-P0-01）

**v1 结论全部平移**（前端纯函数方案，与后端平台无关）：

- 归档实现为纯函数 `archiveState(state, today)`，新文件 `src/core/archive.ts`，挂 `prepareState()` 首步（v1 论证：`prepareState` 是全仓唯一「非用户触发的维护」漏斗，bootstrap/60 秒定时器/备份导入三路径共用，容器零新增副作用分支；幂等保证不制造假 dirty 与额外修订号竞争）。
- 三档窗口（以日龄计）：

| 日龄 | dailyPlans | dailyLogs / freeLogs | archive |
|---|---|---|---|
| ≤ 30 天 | 保留明细 | 保留明细 | 无条目 |
| 31–90 天 | 删除（并入 DaySummary 后丢弃） | 保留明细 | 建档 DaySummary |
| 91–365 天 | 已删 | 删除（并入 DaySummary） | 保留 DaySummary |
| > 365 天 | 已删 | 已删 | DaySummary 并入 MonthRollup 后删除 |

- 窗口依据不变：plans 只有「今天」被业务读取（30 天明细是核对余量）；logs 读深 30 天（周报窗口 `rangeEndingAt`、perfect-week 徽章 7 天）；记录页/冲突弹窗/备份摘要四处的全量 reduce 改「明细 + archive」双读（`src/pages/RecordsPage.tsx:24-34`、`src/app/ConflictDialog.tsx:8-13`、`src/core/storage.ts:181-191`）。
- **256KB 预算核算表平移**：归档后稳态 ≈175–197KB（上限约 197KB、典型 175KB，余量 ≥59KB / ≥23%）；未归档则第 82–113 天触顶 413。plans 压到 30 天即删的理由重申：plans 是可再生成派生数据，不可再生信息（做了几项、几分）已落 DailyLog，删除无信息损失。
- **v2 更新点：256KB 双侧校验**。前端预算照旧；服务端在 `server/src/routes/state.ts` 落 `bodyLimit: 256*1024` + content-length 预检双保险（对齐 v1 `functions/handler.mjs:3,152-163`），413 `payload_too_large` 错误码不变。前端 `oversize` 状态（FR-01-3：`SyncStatus` 增加 `'oversize'`，`pushNow` 识别 `error.code === 'payload_too_large'` 后不走 markDirty 重试，家长区横幅 + 手动同步入口）**原样平移**——`payloadError` 已能透传 code（`src/core/sync.ts:39-51`），协议无需再动。
- 归档走既有 CAS 推送链路、收敛性论证（两台设备对同一状态各自归档得到相同结果，纯函数确定性保证）不变。

### 6.2 contentVersion 与内容 id 迁移（FR-P0-02）

**v1 结论全部平移**（纯前端方案）：

- `SyncState` 加 `contentVersion: string` + `migrations[]`（cap 5 条）两个加性字段；字段放 SyncState 而非云端独立列的理由重申：版本与数据必须随 CAS 快照原子一致，独立列会出现「data 已换新、版本列还是旧值」的中间态，且备份/导入链路覆盖不到。
- 迁移函数 `migrateContent(state)` 放新文件 `src/core/contentMigration.ts`，挂 `prepareState` 首步（先于归档）：`prepareState = migrateContent → archiveState → daily-tick → ensure-plan`；幂等（版本已最新返回原引用），此点必须有测试钉死。
- id 映射表是纯数据，放 `src/data/content/migrations.ts`；悬空清理策略逐字段平移（lessons 改写 key、mistakes/dictationQueue/weakness 删无映射条目、pointers 夹紧、`dailyLogs[].done` 历史 id 保留不动）；不进 `normalizeState`（「归一」与「迁移」两个变更源分开，normalizeState 只兜底默认值）。
- `schemaVersion` **保持 1**：内容版本与状态结构正交。v2 下此结论更强了——服务端只校验 `schemaVersion === 1`（语义平移 `functions/handler.mjs:177`，落 `server/src/routes/state.ts` 校验链第 4 条），不感知 `contentVersion`，换教材**零服务端改动**。
- 迁移外显 + 安全事件类型 `'content-migrated'` 平移（联动 3.4 审计上云：v1 只写 localStorage，v2 同步落 `security_events` 表）。

### 6.3 云端 revision 历史（环形槽位）

**v1 方案 A（独立表 + 环形槽位）结论平移，v2 落地为 Prisma 模型**：

- v1 对比结论仍成立：独立表（方案 A）全面优于行内 JSON 数组列（方案 B）——B 每次推送全量重写 N×256KB、行大小无声膨胀、加剧单行竞争。v2 的 `FamilyStateHistory`（第四章）即方案 A：`@@id([familyId, slot])`，槽位 = `revision % 10`，保留 10 版、每家庭 ≤2.5MB。
- 写入时机：CAS 成功后 `upsert` 对应槽位（v1 为预插空行 + UPDATE，v2 简化为 upsert 惰性建槽，4.3 节）；**历史写失败不阻断主推送**（try/catch 吞掉，响应仍按主更新成功）——v1 结论核对仍成立。
- 接口从 v1 的 `?action=history` 改为 REST（对齐 v2 API 总则）：
  - `GET /api/v1/state/history` → `{ ok, items: [{ revision, updatedAt }] }`（**仅元数据**，避免一次拉 N×256KB）；
  - `GET /api/v1/state/history/:revision` → 单份快照 `{ ok, data, revision, updatedAt }`，无此版本 404 `not_found`。
- **恢复入口不变**：不提供「一键回滚云端」（那会让 revision 倒退、破坏 CAS 单调性）；链路仍是「拉单份快照 → 走既有备份导入（预览-确认）→ 以新修订号推送」（v1 方案 4.4，`src/app/AppProvider.tsx:442-455` 的 importData 链路零改动）。

### 6.4 RISK-01：归档升级窗口风险（核对：v2 下仍成立，防线加一道）

- **风险**（docs/00:66）：归档版本发布后、旧设备升级前，旧客户端一次成功 CAS 推送会把 `archive` 摘要整份抹掉且**明细已删、不可重建**。根因是旧版 `normalizeState` 白名单丢弃未知字段（`src/core/model.ts:341-400`）——**纯客户端行为，与后端在哪个平台无关，v2 下风险不变**。
- **对策平移（4 道）**：① 发布硬闸门——归档版本发布前家庭全部设备逐台确认升级（04 号文档 :214 检查单）；② 首归档前自动备份——每台设备首次破坏性归档前由 AppProvider 落全量快照（复用 `downloadBackup`，`src/core/storage.ts:197-207`）；③ 环形历史兜底——被抹掉后最近 10 版云端快照里仍有带 archive 的版本可恢复（6.3）；④ 专项用例——04 号文档 §3.11 RISK-01/02/03 三层用例。
- **v2 新增第 5 道（服务端防线）**：自托管后服务端可感知 `data.archive`——PUT 校验链第 6 条（3.2 节）：云端行 `archive` 非空而请求缺失该字段 → 400 `archive_wiped`。把「旧客户端静默抹档」变成「显式失败 + 可监控告警（pino warn + 400 计数）」。v1 做不到的原因是当时方案目标「云函数零改动即兼容」（v1 方案 2.7），自托管后无此包袱。04 号文档 RISK-01 用例的预期「旧版 body 被拒（400）**或**走保档合并」——v2 取「被拒」分支，测试落点从 `dev/function-test.mjs`（追加用例 16）改为 `server/test/state.test.ts`。

**周报扫码/短链**：v1 的 `action=share` 方案改为**带 token 的只读路由**：

- `POST /api/v1/report/share`（家长 access token 鉴权）：生成 128-bit 随机 id + **短时效只读 token**（JWT，`typ: "share"`，仅含 `fid` 与 30 天 `exp`，**不能**换取 access、不能写状态、不能读全量状态）；云端只存周报所需的**聚合数据**快照（非全量 SyncState），有效期 30 天——最小暴露面底线与 v1 相同。
- `GET /api/v1/report/shared/:id?token=<share-token>`：扫码设备（如祖辈手机）**无需登录**即可读聚合数据；token 失效返回 401/404，前端只读路由 `/report/shared`（HashRouter）渲染。
- 二维码：纯 TS 编码器放 `src/core/share/qr.ts`（生成 SVG path，无新运行时依赖，符合依赖红线）。
- 底线复述：短链含孩子学习数据——家长主动生成 + 短有效期 + 只读聚合，三条件缺一不可。

## 附：与设计硬约束的总体兼容性声明

1. **CAS**：v2 没有任何绕过 revision 的写路径。后端从「Supabase REST 条件更新」换成「Prisma `updateMany` 条件更新」，CAS 语义逐条平移（第三章）；历史与分享是纯只读扩展；恢复走既有导入链路、以新修订号落库。
2. **归一化**：服务端只校验信封（`schemaVersion === 1`），读侧权威仍是前端 `normalizeState()`；所有新增进云字段（`archive`、`contentVersion`、`migrations`、`shop`、`restDays`、`actualSeconds`）沿用 v1「加性可选字段 + normalize 兜底」模式，`schemaVersion` 保持 1。
3. **纯函数**：`src/core/` 在 v2 改造中零改动（`sync.ts` 仅端点/方法/鉴权头/401 透传四处，仍是无状态契约模块）；token 编排、静默续期、登出清理等新副作用全部落在 `src/app/`（`AppProvider` 与新 `auth.ts`），AppProvider 仍是唯一持有同步与存储副作用的容器。
4. **服务端信封原则（v2 新增）**：服务端不复制 `SyncState` 结构知识、不深验业务字段，业务演进（归档、换教材、P1 各项）对 server 透明——唯一例外是 RISK-01 防线的 `archive` 存在性检查（6.4），这是用最小结构知识换儿童数据不可再生保护的显式权衡。
