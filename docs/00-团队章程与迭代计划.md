## 四、阶段门禁

```
S0 方案冻结（当前）──用户评审 7 份文档──▶ S1 P0 开发──全量回归全绿──▶ S2 P1 开发──▶ S3 发布准备──发布检查单 20 项全勾──▶ 上线
```

**S0 → S1 进入条件**（全部满足）：
1. 用户对 01 的 10 个开放问题给出决策（至少 TOP3：英语旧数据清除还是迁移、PIN 重置门槛方案、每日英语是否入自动计划）。
2. 用户确认 02/03 的技术方案与开发规范无异议。
3. 在源码仓库提交当前脏工作树为**基线 commit**（约 10 个文件未提交，含 `functions/auth.mjs→dev/auth.mjs` 重构；不提交则后续改动不可追溯）。

**S1 → S2 门禁**：P0 四项合入，`npm run build` + `npm run test` + `npm run test:function` 全绿，每项至少 1 条新增回归用例（见 04 用例表），STATUS.md/CHANGELOG.md 同步更新。

**S3 → 上线门禁**：07 发布检查单 20 项全部勾选，其中第 17（首归档前备份落袋）、18（全设备同批升级）为**硬闸门**。

## 七、协作纪律（全员约束）

1. 源码仓库在 S0 阶段绝对只读；S1 起遵循 03-开发规范的 git 工作流（基线 commit、每需求一 commit）。
2. 所有文档/代码引用给 `文件路径:行号`；措辞不超出数据真实口径（家长侧文案尤其如此）。
3. 每个功能改动必须带回归用例（04 用例表为最低集）。
4. 跨文档冲突由 PM 裁决并记录到本文件第五节台账。
5. 用户是唯一的需求决策人：开放问题未经决策不得假设答案进入开发。
