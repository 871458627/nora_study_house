## 一、产品目标与范围边界

### 1.1 产品定位

给二年级孩子的学习管理 SPA：把「今天该学什么」变成约 25 分钟内可完成的几件事（复习、预习、听写、口算、单词），做完即有反馈，用奖励养宠物「小桃」；家长在 PIN 门禁后的周报里看完成率、错题与薄弱知识点。单设备离线可用，多设备经 Deno Edge Function + Supabase 单行表 `family_state` 做 revision CAS 同步（docs/ARCHITECTURE.md:9-20）。

### 1.2 首期发布目标

**P0 四项全部 DoD 通过 + 真实云端环境验证（docs/STATUS.md 第六节发布前清单）完成，方可上云发布。** P0 之外均为后续迭代，不阻断发布。

### 1.3 范围边界

| 范围 | 内容 |
|---|---|
| 首期内（发布版） | 现有学习闭环（今天 / 课本 / 练习 / 听写 / 口算 / 小桃 / 记录 / 周报 / 设置）+ FR-P0-01 状态归档 + FR-P0-02 内容版本与 id 迁移 + FR-P0-03 TTS 真机验证与隐私说明 + FR-P0-04 PIN 重置审计外显 |
| 第二迭代 | FR-P1-01 星星商店 ~ FR-P1-06 家长触达，共 6 项 |
| 路线（第三迭代起） | 见第五节 P2 概要 |
| 明确不做（非目标） | 账号体系与实名认证；服务端判题；任何真实货币支付、抽奖、开箱；社交与排行榜；服务端推送（APNs/FCM）；跨家庭数据共享；除法口算；语音作答与语音识别上云 |

### 1.4 硬约束（所有需求不得违反）

1. 单家庭单行云表 + revision CAS，不做字段级合并（docs/ARCHITECTURE.md:20）；云函数请求体上限 256KB（`functions/handler.mjs:3`）。
2. 状态结构变更必须经 `normalizeState()` 兜底（`src/core/model.ts:282-401`），旧/异常文档不得崩溃。
3. 无 UI 组件库、无图表库，界面全部手写；核心逻辑保持纯函数（`src/core/`），测试用 Vitest。
4. 只存孩子昵称与学习记录，不采集真实姓名、学校、班级、位置、设备标识（README.md:67）；面向未成年人的合规要求见 FR-P0-03。
5. 一切面向孩子的反馈遵循现有原则「奖励只和努力有关，答错不扣奖励」（`src/pages/TodayPage.tsx:196-201`）。

## 三、P0 需求卡（发布阻断，共 4 项）

### FR-P0-01 状态归档与体积控制

**优先级**：P0（发布阻断）　**来源**：评审结论 P0-1

#### 背景与问题陈述

- `SyncState` 持久化三个按日期键控、只增不减的集合：`dailyPlans`、`dailyLogs`、`freeLogs`（`src/core/model.ts:107-109`）；全仓没有任何清理或归档逻辑，日常维护 `prepareState` 只做宠物衰减与当日计划生成（`src/core/state.ts:165-170`）。
- 每天写入 1 条 `dailyPlans`（`generatePlan` 产出约 5 个任务，每任务含 title/subtitle/questionIds/wordIds，评审结论实测约 1.5-2KB/天）与 1 条 `dailyLogs`（约 0.3KB/天），合计约 1.8-2.3KB/天。
- 云函数对 POST 请求体有 256KB 硬上限：`functions/handler.mjs:3` 定义 `MAX_BODY_BYTES = 256 * 1024`，`:152-154` content-length 预检、`:113` 流式累计，超限返回 413 `payload_too_large`（`:163`）。按上述增速，**上线后约 111-142 天（约 4 个月）必然触顶**。
- 触顶后前端表现为「准静默失败」：413 走非 409 错误分支，仅 `setSyncError` + 状态置 `offline`（`src/app/AppProvider.tsx:217-221`），错误码只在设置页同步区以 fallback 文案「同步提示：payload_too_large」出现一行（`src/pages/SettingsPage.tsx:405-408`）；今日页与孩子侧无任何提示，`dirty` 恒为 true，每次 `online`/`visibilitychange` 重试再 413（`src/app/AppProvider.tsx:305-316`），多设备同步从此瘫痪且家长难以定位原因。

#### 用户故事

- 作为家长，我希望应用长期使用后数据仍能可靠同步到另一台设备，而不是几个月后悄悄「同步坏了」。
- 作为开发/运营，我需要在体积接近上限前看到预警，并有确定性的整理手段，而不是收到用户反馈才排查。

#### 功能需求细分

1. **FR-01-1 归档窗口与折叠规则**：维护函数随 `prepareState` 执行（挂接 `src/app/AppProvider.tsx:319-330` 的 60 秒定时路径），将 **90 天前**的 `dailyPlans` 折叠为按日摘要（date、任务数、完成数、计划分钟、实际分钟）；`dailyLogs` 与 `freeLogs` 折叠为**按月聚合**（当月天数、有计划天数、完成项数、星星、桃粮、听写对错、自由练习量）。近 90 天明细保留（周报 30 天窗口 `src/pages/ReportPage.tsx:217` 依赖明细，90 天留足余量）。
2. **FR-01-2 体积监控**：设置页家长区显示当前状态估算字节数与「按近 30 天增速预计还可同步约 N 天」。
3. **FR-01-3 413 明确化**：`pushNow` 捕获 `payload_too_large` 后不再置 `offline` 循环重试，而是进入「体积超限」终态：暂停自动推送、家长区横幅「学习数据过大，需要整理后才能继续同步」、保留手动「立即同步」入口；归档完成体积降回后自动恢复。
4. **FR-01-4 备份与导入兼容**：归档摘要进入 `SyncState`；`normalizeState()` 对「含摘要的新文档」与「不含摘要的旧文档」双向兜底；导出备份仍为全量快照（`src/core/storage.ts:137-148`），归档导致的明细损失可由备份找回。
5. **FR-01-5 周报口径不变**：归档后 7/30 天窗口的所有图表与汇总数值不变；超窗口的历史在周报不展示（现状亦然），不因归档出现断图表。
6. **FR-01-6 验证证据**：新增 `tests/archive.test.ts`（折叠、窗口边界、normalize 兼容）；用构造的 250KB 状态在 `dev/function-preview.mjs` 验证 413 → 前端超限态 → 归档 → 推送恢复全链路。

#### 验收标准（DoD）

- AC1：构造含 >90 天历史的 state 执行维护后，`dailyPlans`/`dailyLogs`/`freeLogs` 明细仅剩近 90 天，摘要字段就位，单测断言体积下降。
- AC2：`normalizeState` 读取「无摘要旧文档」与「有摘要新文档」均不返回 null 且字段齐全。
- AC3：构造 250KB 状态 POST 云函数得到 413；前端同步状态显示「体积超限」而非 offline，且 1 分钟内自动重试次数为 0。
- AC4：归档前后，近 30 天周报各卡片数值逐项相等（单测对拍）。
- AC5：设置页可见状态体积估算与预计可同步天数。

#### 非目标

- 不做云侧多表/分行存储，不改变单行 CAS 协议；不压缩 `mistakes`（已有 300 条上限，`src/core/progress.ts:101`）、`weakness`、`dictationQueue`；不做 gzip 传输压缩。

#### 依赖与风险

- **依赖**：schemaVersion 升级策略（与 FR-P0-02 同一窗口决策，见开放问题 Q9 相关联的风险）；导出备份链路（已有）。
- **风险**：① 归档不可逆——必须先自动导出一份备份再执行首次归档；② schemaVersion gate（`src/core/model.ts:283`）若同步 bump，旧版本前端读到新文档会整份判无效，需在发布节奏上保证所有设备同批升级，或 normalize 支持向后兼容读取。

### FR-P0-02 contentVersion 与内容 id 迁移

**优先级**：P0（发布阻断）　**来源**：评审结论 P0-2

#### 背景与问题陈述

- `SyncState.schemaVersion: 1` 只描述**状态结构**版本（`src/core/model.ts:95,122`），`normalizeState` 只认 1（`:283`）；**没有任何字段标识教材内容版本**。
- 学习状态全部以内容 id 为键：`lessons` 以 lessonId 为键（`src/core/model.ts:100`）、`mistakes` 存 questionId/lessonId（`:29-34`）、`dictationQueue` 以 wordId 为键（`:42-47`）、`weakness` 以知识点 id 为键（`:36-40`）。
- 英语换版已实际暴露问题：课 id/题 id 全变（旧 6 单元 24 课 → 新 `en-u1-l1`…`en-u6-l3`），旧错题、单词掌握度、SRS 到期日仍指向旧 id，在新内容下查不到课，「界面会少显示而非报错」（docs/STATUS.md:20,24）。
- 题 id 与知识点 id 由 builders 按位置生成：`${lessonId}-q${index+1}`（`src/data/content/builders.ts:87`）、`${lessonId}-{p|r}{index}`（`:97`）——内容一旦调整顺序或删题，历史对错数据整体悬空。
- 二下内容上线时将整体重复此问题，必须在首期建立机制。

#### 用户故事

- 作为家长，我希望换教材/换学期后，孩子过去的错题与掌握情况能尽量延续，而不是「清零重来」或变成看不见的死数据。
- 作为开发，我需要有确定的内容版本标识与迁移路径，让二下内容上线不再是一次手工冒险。

#### 功能需求细分

1. **FR-02-1 版本字段**：`SyncState` 增加 `contentVersion`（字符串，如 `g2a-en2024`）与 `migrations: { from: string; to: string; at: string; moved: number; dropped: number }[]`；`normalizeState` 对缺失字段给默认值，不因 `contentVersion` 变化拒绝文档。
2. **FR-02-2 映射表机制**：新增 `src/data/content/migrations/` 目录，按「from→to」提供旧 id→新 id 的映射（lessonId、questionId、wordId、pointId 四类；映射不到的值为 null=删除）。**首期必须交付英语旧版→2024 版映射表**（按单元与 Lesson 序对齐，无法对应的标 null）；映射表须由家长/内容维护者 review。
3. **FR-02-3 迁移函数**：纯函数 `migrateContent(state, migrations)`：遍历 `lessons` / `mistakes` / `dictationQueue` / `weakness` / `pointers` 替换 id，null 条目移除并计数；写 `contentVersion` 与 `migrations`，刷新 `updatedAt`。幂等：对已迁移状态二次执行返回原状态。由 `AppProvider` 启动（bootstrap，`src/app/AppProvider.tsx:260-303`）与备份导入（`importData`，`:442-455`）两处调用。
4. **FR-02-4 迁移结果外显**：家长区设置页显示「内容已从 X 更新到 Y：迁移 N 条记录，移除 M 条无法对应的记录」，并记入安全事件（联动 FR-P0-04 的事件类型扩展）。
5. **FR-02-5 回归测试**：`tests/contentMigration.test.ts` 覆盖四类集合的键替换、悬空清理、计数、幂等、pointers 夹紧（`src/core/state.ts:88-97` 已有夹紧逻辑可复用）。

#### 验收标准（DoD）

- AC1：构造含旧英语 id 的 state（mistakes/lessons/dictationQueue/weakness）载入新内容后，映射到的课在课本页显示历史进度，未映射条目消失且计数正确。
- AC2：家长区可见迁移汇总（版本、条数、时间）。
- AC3：迁移函数对同一状态执行两次，第二次返回全等状态（幂等单测）。
- AC4：仅 `contentVersion` 不同、`schemaVersion` 仍为 1 的文档，`normalizeState` 不返回 null。
- AC5：备份导入旧备份文件后自动完成迁移，导入预览（`src/components/BackupImportDialog.tsx`）显示迁移提示。

#### 非目标

- 不做题目文字相似度等语义自动对齐；不迁移 `stars`/`food`/`streak` 等与内容无关的奖励字段；不改变 builders 的 id 生成规则；不处理「同一版本内的题目微调」（属于内容修正，靠 P2-8 报错入口收集）。

#### 依赖与风险

- **依赖**：开放问题 Q1（英语旧数据清除 or 迁移）直接决定英语映射表的工作量；二下映射表需内容定稿后产出。
- **风险**：映射错误会静默污染掌握度与 SRS 到期日，必须人工 review + 幂等保护；迁移在多设备 CAS 环境下应由「迁移产生 dirty 推送」自然同步，需验证不会与另一台未迁移设备形成 409 循环。

### FR-P0-03 TTS 真机验证 + 应用内隐私说明页

**优先级**：P0（发布阻断）　**来源**：评审结论 P0-3

#### 背景与问题陈述

- 听写是核心闭环，依赖 Web Speech API：`src/app/useSpeech.ts:18-39` 封装 `speechSynthesis`；听写自动播报与喇叭按钮在 `src/features/dictation/DictationSession.tsx:36,74,90,279,291`；英语单词点读在 `src/features/words/WordsSession.tsx:99,171,184-187`；知识卡朗读在 `src/pages/LessonPage.tsx:38`。

### FR-P0-04 PIN 重置审计外显 + 重置门槛提升

**优先级**：P0（发布阻断）　**来源**：评审结论 P0-4

#### 背景与问题陈述

- 现行忘记 PIN 流程：「忘记 PIN？」→ 先导出备份 → 输入「重置」二字 → 清除本机 PIN → **立刻允许设置新 PIN 并进入家长区**（`src/components/PinGate.tsx:151-196`、`:101-121`）。对一个识字的二年级孩子，「导出备份」和照抄「重置」两个字都不构成障碍；而 PIN 的自我定位就是「挡住孩子自己改设置」（README.md:67）。
- 重置已有审计埋点：`recordSecurityEvent('pin-reset')`（`src/app/AppProvider.tsx:371-375`），写入 localStorage `xiaotao-security-events-v1`，保留最近 20 条（`src/core/storage.ts:77-106`，`:100` 截断）。
- **但没有任何界面读取展示**：全仓仅 `AppProvider.tsx:374` 一处调用，不存在 `loadSecurityEvents` 之类的读取方（本次 grep 复核 0 命中），`recordSecurityEvent` 的返回值被丢弃——审计数据沉在 localStorage，家长事后无从察觉孩子重置过 PIN。

#### 用户故事

- 作为家长，我希望即使孩子发现并走通了重置流程，我也能在家长区看到「什么时候被重置过」，并且重置本身没那么容易完成。
- 作为产品方，我需要 PIN 承诺的「挡住孩子」与实际强度一致，不夸大也不裸奔。

#### 功能需求细分

1. **FR-04-1 事件读取 API**：`src/core/storage.ts` 增加 `loadSecurityEvents(): SecurityEvent[]`（容错解析，坏 JSON/超 20 条与写入侧同规则）。
2. **FR-04-2 家长区安全记录卡片**：设置页家长区展示最近 20 条安全事件（类型 + 相对/绝对时间）；最近 7 天内存在 `pin-reset` 时，周报页顶部出现提醒条「本周本机发生过 PIN 重置」。
3. **FR-04-3 重置门槛提升**（方案选择见开放问题 Q4，推荐 a）：
   - a) **恢复码方案**：设置 PIN 时生成并一次性展示 8 位家长恢复码（提示抄写离线保存，设备态存储其哈希）；忘记 PIN 需输入恢复码方可清除；恢复码连错 5 次沿用 PIN 锁定策略（`src/core/pin.ts` failures 机制）；恢复码遗失走 b 兜底。
   - b) **重兜底方案**（保留并强化现流程）：导出备份 + 输入「重置」 + 长按确认 3 秒 + 重置后 24 小时内家长区**只读**（可查看不可改设置、不可导入备份）。
4. **FR-04-4 事件类型扩展**：`pin-set`、`pin-reset`、`pin-fail-lock`、`privacy-confirmed`、`content-migrated` 统一 `{type, at}` 结构，仍保留 20 条。
5. **FR-04-5 会话解锁复核**：多标签/隐身窗口下 sessionStorage 10 分钟共享解锁（`src/core/pinSession.ts`，`src/components/PinGate.tsx:69-94`）在重置与只读限制下行为正确（重置不清除他标签已解锁会话的可见性，但只读限制以事件时间为准不受会话影响）。

#### 验收标准（DoD）

- AC1：家长区可见最近 PIN 重置记录（类型+时间），无需开发者工具；7 天内有重置时周报页有提醒条。
- AC2：按 FR-04-3a——无恢复码无法完成重置；恢复码错误 5 次后锁定；单测覆盖生成、校验、锁定。
- AC3：重置后 24 小时内家长区为只读态（设置项禁用 + 提示），到期自动恢复。
- AC4：五类安全事件均正确写入并在卡片展示，超 20 条滚动截断。
- AC5：`tests/` 新增安全事件读取容错单测（坏 JSON、超长数组）。

#### 非目标

- 不做云端家长账号、短信/邮箱验证（无账号体系）；安全事件不上云（保持设备本地）；不做防截屏等系统级防护。

#### 依赖与风险

- **依赖**：FR-P0-03 的事件类型（privacy-confirmed）；设备态结构变更（`DeviceState`，`src/core/storage.ts:4-12`）需考虑版本兼容（version: 2 → 3 的读取兜底）。
- **风险**：恢复码遗失导致家长自身被挡——导出备份兜底路径必须永远可用且在重置页显著提示；孩子可能拿到恢复码（纸质保管提示要写清）。

**背景与问题**：应用无任何通知机制——全仓无 `Notification` / `serviceWorker` 代码（本次 grep 复核 0 命中；PWA 清单已有 `public/manifest.webmanifest`）；`deadlineHour` 仅用于页面内文案（`src/pages/TodayPage.tsx:73,151,267`）。家长不看设备就不知道孩子当天做没做，周报必须上手孩子的设备并输 PIN。

**用户故事**：作为家长，我希望快到截止时间孩子还没做完时手机能有提醒；也希望在上班时用自己的手机扫个码看一眼周报，不碰孩子的平板。

**功能需求细分**：
1. PWA 本地提醒：注册 service worker + Notification API（纯本地，不接推送服务）——晨间可配置时间提醒、截止前 1 小时未完成提醒；localStorage 记录当日已发标记防重复；权限被拒时家长区显示开启引导；iOS PWA 通知的平台限制在设置页如实说明。
2. 周报只读查看：家长区生成只读访问方式（二维码/链接），打开后仅展示周报汇总（复用 `ReportPage` 数据口径），不可进入任何可修改页面；鉴权方案需与现有平台网关边界（docs/ARCHITECTURE.md:120-121）兼容，具体形式见开放问题 Q8。
3. 提醒设置位于家长区，默认全部关闭。

**DoD**：权限拒绝路径无异常且家长区有引导；同一日「截止前」提醒至多 1 条；只读视图无任何写操作入口（点击所有链接均不可达设置/导入）；iOS/Android 真机提醒行为纳入验证。

**非目标**：不做服务端推送（APNs/FCM）、短信、微信触达。

**依赖与风险**：iOS Safari PWA 通知兼容性需真机验证（并入 FR-P0-03 矩阵）；只读路由鉴权依赖 Qoder Sites 能力，若不可行则降级为「周报截图导出」。
