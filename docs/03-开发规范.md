## 一、分层依赖与纯函数边界

### 1.1 依赖方向（只允许向下）

```
src/data/（纯静态教材数据与查询索引）
   ↑
src/core/（状态模型、归一化、reducer、计划、判分、进度、同步 —— 全纯函数）
   ↑
src/app/（AppProvider 唯一同步/存储副作用容器、路由、浏览器 API hook）
   ↑
src/pages/ · src/features/ · src/components/（展示与输入，经 useApp() 读写）

server/（自托管 Fastify 服务端：routes → services → repositories，与前端只共享 JSON 契约，不 import src/）
dev/ · mockups/.tools/（本地 Node/Playwright 工具，永不随产物部署）
```

依据 docs/ARCHITECTURE.md:24-32 与 docs/02-技术架构方案.md 第二章。检查方法：`src/data/` 不得 import `core|app|pages`；`src/core/` 不得 import `app|pages|features|components`；`server/src/` 不得 import 任何前端 `src/` 路径（v1 的 `functions/handler.mjs` 零 import 是同一纪律的先例）。服务端不复制 `SyncState` 的 TS 类型——字段语义唯一权威在前端 `src/core/model.ts`，服务端只校验信封（`schemaVersion === 1`，语义平移自 functions/handler.mjs:177）；唯一例外是 RISK-01 防线的 `archive` 存在性检查（docs/02 §6.4）。

### 1.2 `src/core/` 纯函数边界：能做与不能做

**能做**（均有先例）：

- 一切以入参到返回值的推导：状态变换、计划生成（`src/core/plan.ts:199`）、判分（`src/core/grading.ts:31`）、启动决策（`src/core/syncBoot.ts:20-27`）。
- 「当前时间」作为**可注入的缺省参数**：`action.date ?? todayKey()`（`src/core/state.ts:54,101,117`）、`decayPet(pet, date)`——测试传显式日期即可确定性复现。
- `updatedAt: new Date().toISOString()` 这类时间戳刷新（`src/core/progress.ts:258`）：这是全层唯一被容忍的非确定来源，因为测试从不断言时间戳本身，只断言它被刷新（容器靠它判断推送期间又有改动，`src/app/AppProvider.tsx:201`）。
- 抛出携带结构化信息的错误对象（`SyncError`/`ConflictError`，`src/core/sync.ts:9-29`）——但不得发起网络请求本身。

**不能做**（反例，均无既有代码可寻，也不许出现）：

```ts
// 反例 1：core 里读 localStorage —— 副作用只允许在 AppProvider
export function loadPlan(date: string) {
  return JSON.parse(localStorage.getItem('plan') ?? '{}');   // ✗
}

// 反例 2：core 业务函数里 fetch —— 业务推导不得依赖网络
export function planWithRemoteState(date: string) {
  const res = await fetch('/api/v1/state'); // ✗ IO 只允许容器编排（sync.ts 契约模块经注入的 getAccessToken 取 token，见 docs/02 §5.1）
}

// 反例 3：Math.random() —— 用种子随机（src/core/grading.ts:3 seededRandom）保证可测
const index = Math.floor(Math.random() * options.length);    // ✗

// 反例 4：不经参数注入的时间 —— 测试无法构造「昨天」
const yesterday = todayKey(-1);                              // ✗ 应由调用方传入 date
```

> 关于 `fetchRemote`/`pushRemote`（`src/core/sync.ts:93,108`）的定位：它们是现状放在 core 文件里的**契约模块**——无 React 依赖、无内部状态、可整体替换，其调用编排（何时 fetch、何时 push、错误怎么呈现）全部在 AppProvider（`src/app/AppProvider.tsx:200,239,263`）。新增云接口（如 fetchHistory）并入 `sync.ts` 同一契约模块即可；但**不得**在 core 的业务推导（计划、判分、进度、归一化）里直接调用 IO。

### 1.3 `AppProvider`：唯一副作用容器

定时器、fetch 调用编排、localStorage 读写、PIN 加盐（WebCrypto）都只在 `src/app/AppProvider.tsx`（docs/ARCHITECTURE.md:32）。两条强制约定：

1. **双分发同步**：`dispatchLocal` 先 `dispatch(action)` 再 `stateRef.current = appReducer(stateRef.current, action)`（`src/app/AppProvider.tsx:340-348`），因为推送读的是 `stateRef` 而非 React 状态。新增任何「容器内直接改状态」的路径都必须同样维护 `stateRef`，否则推送会发旧快照。
2. **副作用 hook 归 `src/app/`**：浏览器 API 封装 hook（`useSpeech.ts`，规划中的 `useActiveSeconds.ts`）与 AppProvider 同层，不得下沉到 core、不得上浮到 pages。

### 1.4 `server/` 边界

- 不 import 前端 `src/`；与前端只共享 JSON 字段契约（响应形状见 docs/02-技术架构方案.md 第三章 API 契约）。
- 校验失败返回标准错误体 `{ error: { code, message } }`，不带内部细节（先例：v1 `functions/handler.mjs:11`，503 用例明确断言无 `message` 泄漏，`dev/function-test.mjs:262-265`；v2 错误码集中定义于 `server/src/errors.ts`，见 8.2）。
- 任何接口扩展保持旧客户端可用（先例：新资源/路径走 `not_found` 404，见 docs/02 §6.3）。
- 自托管后服务端是唯一入口、无平台网关兜底：**每个新路由上线前必须回答「要不要鉴权、要不要限速」并写在路由表注释里**（红线见 8.4 与 docs/02 §2.3）。

## 二、测试规范

### 2.1 基数与命令

| 命令 | 现状 | 门槛 |

### 2.2 每个功能需求至少 1 个回归用例

- **需求 → 用例可追溯**：STATUS.md 第二节「回归测试」列就是台账（docs/STATUS.md:32-52）。历史欠账是 9 项修复无自动测试（docs/STATUS.md:75-76）——不许再增加。P0/P1 每项 FR 的验收标准里至少一条写成可执行断言。
- **先抽纯函数再测**：编排逻辑不直接测容器，抽成纯函数后测。先例：启动决策从 AppProvider 抽出 `decideBootstrap`（`src/core/syncBoot.ts`），配 8 例含「同修订号 + dirty 不加冲突」（docs/STATUS.md:34）。规划中的归档、内容迁移全部按此模式（见 docs/02 第二章、第六章）。
- **缺陷修复必须带用例**：修 bug 的 commit 里同时给「复现该 bug 的失败断言」。先例：P0-01 修复与 `tests/syncBoot.test.ts` 同批（git: `701cad2`）。

### 2.3 命名与放置

- 放置：`tests/` 平铺，一个 core 模块或一个特性域一个文件（现有 14 个文件的粒度：`plan`、`grading`、`progress`、`weakness`、`oralMath`、`englishPractice`、`englishContent`、`freePractice`、`freeDictation`、`syncBoot`、`storage`、`pinSession`、`currentLesson`、`core`）。
- 命名：`describe` 写行为域（`describe('English content matches the 2024 textbook')`，`tests/englishContent.test.ts:51`）；`it` 写一句可判真伪的陈述（`it('has the six units of this edition, in order')`）；**断言消息用中文**，失败输出直接面向中文团队（`expect(spellCount, '${lesson.title} 拼写题不足')`，`tests/englishContent.test.ts:89`）。
- 顶部注释写「这份测试钉死什么、为什么」（`tests/englishContent.test.ts:5-9` 说明教材版本与防退化动机）。

### 2.4 禁止跨 AppProvider 边界

- 测试**默认不得** mount `AppProvider`、不得 mock `fetch`/`localStorage` 进容器——绝大多数用例是纯函数与独立存储单元（jsdom 下 `pinSession`/`storage` 直接用真实 sessionStorage/localStorage，`tests/pinSession.test.ts:21-52`）。
- 需要测容器行为时，说明设计错了：把逻辑下沉为纯函数（2.2 第 2 条）。
- **唯一白名单**：跨契约编排流允许「真实容器 + 仅 stub `globalThis.fetch`」的组件级集成测试（`localStorage` 仍用 jsdom 真实实现），当前仅 `tests/bindFlow.test.tsx`（首次绑定流程，docs/06 §3.10）——它钉的是 auth 与 state 两个契约接进 UI 分流的接线，逻辑下沉为纯函数只会得到空洞断言，故豁免。新增白名单成员必须在 02/06 号文档有对应设计小节，并在测试文件顶部注释写明理由。
- 浏览器交互回归用 `mockups/.tools/*.mjs` Playwright 脚本（产出 `screenshots/acceptance/`），它是补充而非替代——STATUS.md:76 已把 P1-01/P1-02 这类布局与弹窗缺陷归为「最需要脚本兜住」的一类。

## 三、git 工作流

### 3.1 基线先行

开工 P0 任何一项之前：交付仓库若尚无 `.git` 则 `git init`；**先把当前工作树（快照代码 + 全部文档）原样提交为基线 commit**，不得混入首个需求的改动——保证后续每个需求 commit 都能在干净基线上单独回溯与 review。基线 message 建议 `chore: 交付基线快照（含 01-03 号文档与只读代码快照同步）`。

### 3.2 每需求一 commit

一个 FR（或一个缺陷修复）一个 commit；commit 内自洽：代码 + 测试 + STATUS/CHANGELOG 同批更新。禁止「顺手」携带无关文件改动；大型需求确需拆分时用同一 scope 的连续 commit（如 `feat(core): 归档纯函数层与单测` → `feat(app): 归档接入 prepareState 与首归档备份` → `feat(ui): 记录页双读归档摘要`）。

**配套改动必须同 commit（事故教训，2026-10-25）**：跨文件引用的两侧——页面与其调用的 Provider 方法、接口声明与实现、类型定义与消费方——**只能存在于同一个 commit 里**，禁止「先提交调用侧、实现下个 commit 补」。

> **事故实录**：`e9026b4` 提交了 `OnboardingPage.tsx` 对 `bindLogin/bindRegister/bindPull` 的调用，但 `AppProvider.tsx` 的对应实现（49 行）留在工作区未提交。远程 main 从此 `tsc` 失败（`error TS2339`），Render 自动部署连败 3 次，线上停在旧版本，直至 `c0bbf1a` 补交才恢复。
>
> **提交前自问：把仓库克隆到新机器、checkout 到这个 commit，能编译通过吗？** 答案必须永远是「能」。守住它的机械手段见 3.4 提交门槛。

### 3.3 commit message：沿用仓库既有风格

格式 `type(scope): 中文描述`（scope 可省略）。仓库 15 个既有提交的实际用例（`git log --oneline` 核对）：

| type | 实例 |
|---|---|
| `feat(scope)` | `feat(core): 业务逻辑纯函数层与单元测试`；`feat(data): 英语内容换成北京出版社 2024 审核版预备级二上`；`feat(functions): 云函数与本地联调工具`；`feat(ui): 应用外壳、页面与答题会话` |
| `fix(scope)` | `fix(sync): 同修订号的未上传改动保留本机并立即推送` |
| `docs(scope)` | `docs: README/架构/现状/更新日志同步到换版后的实测状态`；`docs(content): 英语课本逐页核对表，作为内容定稿依据`；`docs(acceptance): 第二轮修复与本地复验记录` |
| `chore` | `chore: 工程骨架与构建配置` |
| `assets` / `design` | `assets: 设计效果图、验收截图与浏览器验收脚本`；`design: 小桃学习屋六屏高保真效果图` |

scope 取层名或域名：`core`/`data`/`ui`/`server`/`sync`/`content`/`acceptance`（`functions` 为 v1 历史 scope，随平台退场，新提交一律用 `server`，如 `feat(server): 自托管 API 骨架与状态 CAS 路由`）；新增域（如归档、迁移）优先复用层名。描述用一句动宾短语中文，不加句号，不用英文。

### 3.4 提交门槛（强制，任何一环红则不提交）

1. **commit 前**：`npm run check` 全绿（根目录脚本 = web 的 `tsc --noEmit` + server 的 `tsc --noEmit`；这是拦截「调用侧已提交、实现侧遗漏」的第一道闸，见 3.2 事故实录——`tsc` 对缺失的接口成员会当场报 `TS2339`）。
2. **commit 前**：`npm run test` 全绿（web + server 全部用例）。
3. **push 前**：`npm run build` 全绿（等于线上 Render 构建的前半段，确保远程自动部署不会失败）。
4. 触及 `server/` 的提交另加 `npm run test --workspace server && npm run check --workspace server` 两连全绿；改 `server/prisma/schema.prisma` 的提交必须包含生成的迁移文件，且根 `package.json` 与 `server/package.json` 的脚本保持同步。
5. push 前在同分支 rebase 确认无冲突。

速查（任何提交走完这三条再 push）：

```bash
npm run check && npm run test && npm run build
```

### 3.5 分支工作流（2026-10-27 用户裁定，即时生效）

**main 分支只接受已验收的代码。一切开发（新需求、缺陷修复、文档变更概莫能外）必须先开分支，验收通过后才能合并回 main。** main 的每次 push 都会触发 Render 自动部署，因此「合并进 main」就等于「上线」——验收闸门守的就是这一步。

**1. 开分支**：从最新 main 切出，命名 `<type>/<短名>`（如 `feat/sports-calendar`、`fix/reader-cancel`、`docs/branch-policy`）。开工前 `git pull` 确保基线最新。

**2. 分支上开发**：commit 规范同 §3.2–3.4（每需求一 commit、配套改动同 commit、提交门槛三连）。**双窗口并行注意**：两个窗口共用同一工作树，同一时刻只能存在一个分支——各窗口开分支前必须先协调；更稳妥的做法是为每个窗口建独立克隆（`git clone` 第二目录）或独立 worktree，各自在自己分支上开发。

**3. 验收闸门（合并的前置条件，三条全过才许合并）**：
   - **机械验证**：在干净 worktree（`git worktree add ../check <branch>`）里跑完整链路——`npm ci` → `npm run check` → `npm run test` → `npm run build`（web 构建 + `prisma generate` + server 构建）——与 Render 构建环境等价。**本地工作树全绿不算数**（事故教训：并行开发下工作树常混有未提交文件，只有干净树才等价于线上构建）；
   - **功能验收**：按 docs/04 验收矩阵（或需求约定的验收口径）在浏览器/真机走通该需求主路径；
   - **提交集自洽**：`git status` 干净、分支上每个 commit 满足 §3.2 的「克隆到新机器能编译」标准。

**4. 合并与上线**：`git checkout main && git merge --no-ff <branch>`（保留需求边界）→ `git push origin main` → Render 自动部署 → 线上抽查该需求主路径 → `git branch -d <branch>`。合并前若 main 有新提交，先在分支上 rebase。

**5. 机械强制（可选）**：在 GitHub 仓库 Settings → Branches 对 `main` 开启分支保护（禁止 force push；如需强制走 PR 则开启 require pull request）。未开启前，本节靠执行纪律约束。

### 4.2 格式要点（照现有文件）

- **STATUS.md**：文件头注明核对时间与「行号以本次快照为准，后续提交可能漂移」（docs/STATUS.md:3-5）；代码证据一律 `文件路径:行号`；回归测试列诚实标注 ❌（无测试就写无，不许空着装作有）；「有意保留的行为」单独成节（docs/STATUS.md:53-65），防止后人当 bug 重修。

- **文档必须与代码对得上**：docs/STATUS.md:67-69 记录了验收报告与源码不符的一句描述，并明确「复验时请勿按…去找」——写文档时若发现自己拿不准某守卫在哪一层，先读代码再落笔。

## 五、代码风格

### 5.1 TypeScript

- `tsconfig.json` 全开：`strict: true` + `noUnusedLocals` + `noUnusedParameters` + `noFallthroughCasesInSwitch` + `isolatedModules`（tsconfig.json）。新代码不得用 `any`/`as any` 绕过；外部数据一律走 `unknown` + 收窄（`isRecord` 模式，`src/core/model.ts:183-185`）。

### 5.3 注释原则：英文为主，只写代码无法表达的约束

- 默认不注释；要写就写「为什么、约束是什么」，不复述代码在做什么。英文 JSDoc/行注为主（与现有代码一致），面向孩子的文案与测试断言消息除外（中文）。
- 正面实例（各代表一类值得写的注释）：
  - 设计约束与不变量：`src/core/syncBoot.ts:11-19` 整段解释「同修订号不是冲突，因为远端修订号只在推送成功时移动」；

  - 外部系统形状说明：`functions/handler.mjs:45-46`「The platform database client resolves queries to `{ data, error }` … Accept a single object too so local substitutes behave alike.」；

## 六、内容数据规范

### 6.1 builders seed 模式

题目/单词一律经 `src/data/content/builders.ts` 的 seed 构造函数生成，**禁止手写完整 Question 对象**：

| seed | 用途 | 位置 |
|---|---|---|
| `choice(stem, options, answerIndex, explanation?)` | 单选 | builders.ts:15-20 |
| `truefalse(stem, answer, explanation?)` | 判断 | builders.ts:22-28 |
| `match(stem, pairs, explanation?)` | 连线 | builders.ts:30-34 |
| `order(stem, items, explanation?)` | 排序 | builders.ts:36-41 |
| `numeric(stem, answer, explanation?)` | 数字作答 | builders.ts:43-48 |
| `dictationWord(id, word, pinyin)` / `englishWord(id, en, zh, sentence, sentenceZh)` | 听写词 / 英语单词短句 | builders.ts:50-62 |

规则：

1. **题 id 自动生成**：`${lessonId}-q${index+1}`（builders.ts:87），内容文件不写 id；这也意味着题 id 的稳定性取决于 seed 在数组里的位置——**已发布内容的 seed 数组中间不许插行/删行**（会静默改 id，制造悬空引用），只能追加。
2. **知识点归属**：seed 可显式声明 `pointIndexes`，未声明时按 `index % kpIds.length` 轮转（builders.ts:81-91）。现状全库零声明、实际全轮转（docs/STATUS.md:65）——**新增内容应显式声明 pointIndexes**，逐课补标注是内容侧长期工作。
3. 版本与 id 映射：换教材走 docs/02 第三章的 `MIGRATIONS` 数据文件，不许直接覆盖内容文件后不管旧 id。

### 6.2 新增题型 checklist（8 步，缺一不可）

1. `src/data/types.ts`：`QuestionType` 联合加成员 + `Question` 加可选字段（比照 `pairs?`/`items?`/`answer?`，types.ts:12-23）。
2. `src/data/content/builders.ts`：加 seed 构造函数（比照 `numeric()` 的最简形态）。
3. `src/core/grading.ts`：`isResponseCorrect` 加判分分支（grading.ts:31），必要时 `answerText`/展示辅助同步（grading.ts:97）。
4. 会话组件加渲染与作答交互分支（`src/features/practice/PracticeSession.tsx`）。
5. 内容文件用新 seed 出题（`src/data/content/*.ts`）。
6. `tests/grading.test.ts`：对/错/边界三态判分用例。
7. 内容钉死测试扩展（见 6.3）：新题型的自编题按其答案判为正确 + 结构断言。
8. 若计划生成会命中该题型：`tests/plan.test.ts` 补断言；若上云字段结构受影响：`normalizeState` 兜底 + `tests/core.test.ts`。

### 6.3 内容钉死模式（照 `tests/englishContent.test.ts`）

内容是产品事实（哪一版教材、几课、什么顺序），必须用测试钉死防退化，五件套：

1. **顶部注释写版本依据**：哪个版本、资料来源、防什么退化（englishContent.test.ts:5-9 写明 2024 审核版与旧版差异）；
2. **期望值常量钉死**：`EXPECTED_UNITS`/`EXPECTED_LESSONS` 整数组 `toEqual`（englishContent.test.ts:10-39），不许逐条 `toContain` 糊弄顺序；
3. **结构下限断言**：每课 ≥N 预习点/复习点/题/词（englishContent.test.ts:71-79）；
4. **可练习性约束**：受 `buildWordPractice` 规则限制的字段（字母不重复、句子词数 ≥3 等）逐课断言，失败消息中文点名（englishContent.test.ts:81-92）；
5. **判分自洽**：每道自编题以其-authored 答案判为正确（englishContent.test.ts:94-108），错答案/漏字段的内容 bug 直接红。

新增科目或换版时**必须**产出同款测试文件（语文/数学当前尚无内容钉死测试，补齐属内容侧欠账，不阻断代码需求）。

## 八、后端开发规范（server/，v2 新增）

适用于 `server/` 全部代码（Node.js 20 LTS + TypeScript + Fastify + Prisma + Zod + pino）。架构蓝图见 docs/02-技术架构方案.md。

### 8.1 分层职责（routes → services → repositories）

| 层 | 只做 | 不做 |
|---|---|---|
| `routes/` | 路由注册、HTTP 方法与路径、**Zod 校验**（body/query/params/headers）、鉴权前置（JWT 校验钩子）、限速挂载、把领域错误映射为标准错误体与状态码、pino 请求日志 | 任何业务判定（不做 CAS 比较、不判 token 是否该吊销） |
| `services/` | 业务规则：CAS 冲突判定、access 签发与 refresh 轮换/吊销/复用检测、审计事件写入、聚合读 | **不碰 HTTP**：不得 import fastify、不得读 `request`/`reply`、不得返回 HTTP 状态码；错误一律 throw 带错误码的 `AppError`（`server/src/errors.ts`） |
| `repositories/` | Prisma 查询封装（点查、条件更新、upsert、批量删除） | **不含业务**：不在此层决定 409/403/401，函数名与参数用领域词汇（`casUpdateState`）而非 HTTP 词汇 |
| `lib/` | 无业务的基础设施：argon2 封装、JWT 签验、crypto 随机 token、可注入时钟 | 不依赖 routes/services/repositories |

依赖方向 `routes → services → repositories → prisma client`，禁止反向 import；service 之间可调用但不得成环。理由：v1 把全部逻辑塞进单文件 `functions/handler.mjs` 是「平台函数无框架」的权宜，v2 有框架就要按层还债——service 无 HTTP 依赖才能脱离 fastify 单测，repository 无业务才能换库不改逻辑。

### 8.2 校验与错误

- **Zod schema 定义在 route 层**（`server/src/routes/schemas.ts`），service 收到的一律是已校验的强类型对象；校验失败统一 400 `invalid_body`——zod 细节只进 pino 日志（debug 级），响应只给 `code + 固定中文 message`，不透出内部结构（沿袭 v1「无 message 泄漏」用例断言，`dev/function-test.mjs:262-265`）。
- **错误码集中定义** `server/src/errors.ts`：单文件枚举全部 `error.code` + 对应 HTTP 状态码 + 默认 message。禁止在 route/service 里散落字符串字面量（对照前端 `MAX_BODY_BYTES` 的常量纪律，5.2 节）。新增错误码 = 改一个文件 + 一条测试用例（见 8.5）。
- 所有响应（含错误）经统一序列化出口；状态类接口一律 `cache-control: no-store`（平移 v1 `functions/handler.mjs:5-9`）。

### 8.3 Prisma 使用规范

- `server/prisma/schema.prisma` 是数据库唯一真相；改表必走 `prisma migrate dev --name <语义名>` 生成迁移并**同 commit 提交迁移文件**；生产只允许 `prisma migrate deploy`，**禁止 `prisma db push` 上生产**。
- 业务查询一律走 Prisma Client（`findUnique`/`updateMany`/`upsert`…）；原生 SQL 仅允许出现在迁移文件与 repository 的 `$queryRaw`（必须带注释说明 Client 为何表达不了）。
- CAS 一律用 `updateMany({ where: { …, revision: baseRevision } })` 以返回 count 判定成败，**禁止「先读后写」两步假装原子**（原子条件更新先例：v1 `functions/handler.mjs:84-101`）。
- 事务（`prisma.$transaction`）只允许在 service 层使用，且须注释说明需要原子性的理由；repository 单查询不开事务。
- 历史槽位等「惰性初始化」用 `upsert`，不做预插全量行的迁移。

### 8.4 鉴权与 secret 管理红线（一票否决）

以下与 docs/02 §2.3 配套，违反任一条 review 直接打回：

1. **secret 不入库、不入前端产物**：`JWT_SECRET`、`DATABASE_URL`、VAPID 私钥不得进 git 仓库（只提交 `.env.example` 键名）、不得写入 Docker 镜像层、不得进入 `dist/` 产物、不得出现在任何日志（pino 启动即 redact `authorization`/`cookie`/`set-cookie`）。
2. **密码与 token 只存哈希**：密码 argon2id（参数固化于 `server/src/lib/argon2.ts` 常量），refresh token 只存 SHA-256 哈希；明文与哈希永不落日志。
3. **新路由必须显式回答鉴权与限速**：每个 route 文件头部注释两行「鉴权：…；限速：…」，`/api/v1/health` 之类显式写「无鉴权（原因：健康检查）」。登录 5 次/15 分钟 per IP+用户名为下限。
4. **身份只信 token**：`familyId` 一律取自 JWT claims，绝不取自请求体或 query（平移 v1 `functions/handler.mjs:193-198` 原则）。
5. **时间一律注入**：service 判过期/时间戳用注入的 `clock`（`server/src/lib/clock.ts`，默认 `() => new Date()`），测试可固定——对照 core 层「时间可注入」纪律（1.2 节）。

### 8.5 后端测试

- 放置 `server/test/` 平铺一文件一域（与前端 `tests/` 分离，因运行环境不同）；supertest 驱动真实 Fastify 实例 + **真实测试数据库**（`DATABASE_URL` 指向 `xiaotao_test`；`beforeAll` `migrate deploy`，`afterEach` truncate 六表），不复活 v1 的内存假库。
- 每个对外错误码至少 1 条触发用例（「错误码表新增行 = 测试新增行」）；v1 31 个函数 check 的平移映射与 v2 新增用例清单见 docs/02 第八章。
- 不 mock Prisma 查询实现（mock repository 边界可以，mock SQL 行为不行——真实数据库就是被测真相的一部分）；限速用例通过注入测试时钟或临时窗口参数实现确定性。
