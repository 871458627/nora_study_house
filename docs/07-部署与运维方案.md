### 1.2 信任边界逐条说明

| 边界 | 信任判断 | 依据 |
|---|---|---|
| 浏览器 | **完全不可信**。任何客户端都能伪造请求体；身份头（如 `X-Forwarded-For`）到达 nginx 前一律不可信 | v1 结论平移；`familyId` 只信 JWT claims（02 §2.2-2） |
| nginx | 可信的**传输层**入口，但不含身份判断；反代时附加的 `X-Forwarded-*` 头供 api 参考，api 须配 `trustProxy` 才能把真实 IP 用于限速键 | 02 §2.2-1；§3.4 配置注记 |
| api | **唯一身份信任锚**（v1 的平台网关角色由它接管）：JWT 签名校验、argon2id 凭据、限速、body 信封校验全部在此完成；无上游兜底，失守即直面数据库 | 02 §2.2-2「API 成为唯一业务入口，必须自我防卫」 |
| postgres | 内网专属，无公网口；单家庭数据无行级隔离需求（与 v1 判断一致），隔离靠「只有 api 能连」；备份文件含全量家庭数据，按敏感物管理（§7） | 02 §2.3-5 |
| 与 v1 的关键差异 | v1 依赖平台的三道前提（网关可信身份、平台 TLS/限流、站点私有访问控制）**全部消失**——本方案里没有任何「平台兜底」，每条红线违反即等于裸奔 | 02 ADR-001「后果（义务）」 |

### 1.3 职责一句话表

| 层 | 做什么 | 不做什么 |
|---|---|---|
| nginx | TLS、静态文件、缓存头、反代、安全响应头 | 不做鉴权、不碰数据库 |
| api | 鉴权、限速、CAS 同步、token 生命周期、审计、日志 | 不深校验业务字段（信封原则，02 硬约束④）、不直接暴露公网 |
| postgres | 存储、持久化 | 不出内网、不接受外部连接 |

## 2. 环境要求

| 项 | 最低建议 | 说明 |
|---|---|---|
| 计算 | **2C2G 起步**（云厂商轻量应用服务器，或 J4125/N100 迷你主机、带 Docker 的 NAS） | 三容器家庭负载（2–3 台设备）很低；2G 内存下 postgres 与 api 常驻合计约 600–900MB，留有余量 |
| 磁盘 | 40GB SSD | 数据库本体（含 10 槽历史）MB 级；磁盘主要被镜像、日志、7 天备份占用 |
| 网络 | 公网 IP（家庭宽带无公网 IP 时可用 DDNS + 可用端口）；上行 ≥10Mbps | 证书与域名指向依赖公网可达 |
| 系统 | Ubuntu 22.04 / 24.04 LTS 或 Debian 12 | 本文命令以此为准；NAS（如群晖 Container Manager）可导入同一 compose 文件，操作等价 |
| 域名 | **必备**一个（Let's Encrypt 签发前提） | DNS A 记录指向服务器公网 IP |
| 云厂商取舍 | 国内（阿里云/腾讯云轻量）国内访问快但域名须完成 ICP 备案；海外/香港节点免备案但大陆访问延迟明显——二选一，按家庭使用位置定 | 一句话口径，不展开 |

### 3.2 docker-compose.yml

```yaml

# 使用前替换 <your-domain> 类占位符；.env 与本文件同目录（§3.6）
name: xiaotao

services:
  nginx:
    image: nginx:1.27-alpine
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
      - ./nginx/snippets:/etc/nginx/snippets:ro
      - ./nginx/certs:/etc/nginx/certs:ro            # Let's Encrypt 证书
      - ./nginx/www/certbot:/var/www/certbot:ro      # ACME webroot（续期）
      - ./frontend:/usr/share/nginx/html:ro          # dist 版本化目录（current 相对软链）
    depends_on:
      - api
    logging: &default-logging
      driver: json-file
      options: { max-size: "10m", max-file: "3" }
    networks:
      - edge

  api:
    image: ${API_IMAGE}          # 如 xiaotao-api:2026-10-25-g3e79e06，发布/回滚改 .env 这一行
    build: ./server              # docker compose build 时按 image 名打 tag
    restart: unless-stopped
    environment:
      NODE_ENV: production
      PORT: "3000"               # 本部署约定；实现不同时以 server 配置为准，同步改 nginx 反代
      TZ: Asia/Shanghai
      DATABASE_URL: postgresql://xiaotao:${POSTGRES_PASSWORD}@postgres:5432/xiaotao?schema=public
      JWT_SECRET: ${JWT_SECRET}
      ACCESS_TOKEN_SECRET: ${ACCESS_TOKEN_SECRET:-}  # 可选，见 §3.6 说明
    depends_on:
      postgres:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "node", "-e", "fetch('http://127.0.0.1:3000/api/v1/health').then(r=>{if(!r.ok)process.exit(1)}).catch(()=>process.exit(1))"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 20s
    logging: *default-logging
    networks:
      - edge
      - data
    # 刻意不写 ports：api 仅经 nginx 反代可达，不直接暴露

  postgres:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: xiaotao
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: xiaotao
      TZ: Asia/Shanghai
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U xiaotao -d xiaotao"]
      interval: 10s
      timeout: 5s
      retries: 5
    logging: *default-logging
    networks:
      - data

  data: {}

  postgres-data: {}
```

### 3.3 nginx 站点配置

`/opt/xiaotao/nginx/snippets/security-headers.conf`：

```nginx
# 安全响应头（snippet 被各 location 重复 include：
# nginx 规则是 location 内一旦出现 add_header，server 级 add_header 不再继承，
# 因此每个自定义缓存头的 location 都必须重新 include 本文件）
add_header Strict-Transport-Security "max-age=31536000" always;
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header Referrer-Policy "no-referrer" always;
add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
```

`/opt/xiaotao/nginx/conf.d/xiaotao.conf`：

```nginx
# 80 端口：仅 ACME HTTP-01 验证 + 301 跳 HTTPS（红线：任何 API 不得经明文 HTTP 可达）
server {
    listen 80;
    server_name <your-domain>;

    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }

    location / {
        return 301 https://$host$request_uri;
    }
}

server {
    listen 443 ssl;
    http2 on;
    server_name <your-domain>;
    server_tokens off;

    # --- TLS（Let's Encrypt；初次签发与续期见 §5.5/§5.6）---
    ssl_certificate     /etc/nginx/certs/live/<your-domain>/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/live/<your-domain>/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 1d;

    # --- 安全响应头 ---
    include snippets/security-headers.conf;

    # --- 静态根：current 软链指向 releases/dist-<版本> ---
    root  /usr/share/nginx/html/current;
    index index.html;

    # 请求体上限：业务上限 256KB（02 §3.2）+ 余量，nginx 层预拦超大请求
    client_max_body_size 300k;

    gzip on;
    gzip_types text/css application/javascript application/json image/svg+xml;
    gzip_min_length 1024;

    # --- /api 反代：API 为唯一业务入口 ---
    location /api/ {
        proxy_pass http://api:3000;          # 不带 URI，原样透传 /api/… 路径
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 5s;
        proxy_read_timeout    30s;
        proxy_send_timeout    30s;
    }

    # --- 带内容哈希的构建产物：一年 immutable ---
    location /assets/ {
        include snippets/security-headers.conf;
        add_header Cache-Control "public, max-age=31536000, immutable";
    }

    # --- 入口与根级文件：不缓存（孩子设备能否及时升级依赖此条）---
    location = /index.html {
        include snippets/security-headers.conf;
        add_header Cache-Control "no-cache";
    }
    location = /sw.js {
        include snippets/security-headers.conf;
        add_header Cache-Control "no-cache";
    }
    location = /manifest.webmanifest {
        include snippets/security-headers.conf;
        add_header Cache-Control "no-cache";
        types { application/manifest+json webmanifest; }
    }

    # --- 其余静态文件与 SPA fallback（HashRouter 下主要为兜底）---
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

### 3.4 配套代码侧注记（部署前须核对，落在 §4 A 组检查项）

1. **限速取真实 IP**：api 必须以 `trustProxy` 信任 compose 内网一跳（nginx），`@fastify/rate-limit` 的 keyGenerator 取 `X-Forwarded-For` 首个 IP——否则全部请求在 api 看来来自 nginx 内网 IP，按 IP 限速会全家误伤、按 IP+username 限速会全局误锁。
2. **pino redact**：启动即配置 redact `authorization` / `cookie` / `set-cookie`（红线「不入日志」），上线验证方法见 §4 D12。
3. **api 镜像入口**：按 02 §4.3，入口脚本在监听前执行 `prisma migrate deploy`（幂等）；镜像内需保留 Prisma CLI，否则手工迁移命令（§5.4）不可用。

```bash

  -H 'content-type: application/json' \
  -d '{"username":"<家长用户名>","password":"<家长密码>"}'
# 期望 201 + accessToken + Set-Cookie: xiaotao_refresh=…; Path=/api/v1/auth;
#       HttpOnly; Secure; SameSite=Strict

# (4) 登录，提取 accessToken

  -H 'content-type: application/json' \
  -d '{"username":"<家长用户名>","password":"<家长密码>"}' \
  | sed -n 's/.*"accessToken":"\([^"]*\)".*/\1/p')

# (5) GET state —— 期望 200 {"ok":true,"data":null,"revision":0} + cache-control: no-store
curl -sS -i "$BASE/api/v1/state" -H "authorization: Bearer $TOKEN"

# (6) PUT state 首写 —— baseRevision=0，期望 200 revision=1
cat > /tmp/smoke-payload.json <<'EOF'
{"data":{"schemaVersion":1,"onboarded":false,"updatedAt":"2026-10-25T00:00:00.000Z"},"baseRevision":0}
EOF
curl -sS -i -X PUT "$BASE/api/v1/state" -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' --data-binary @/tmp/smoke-payload.json

# (7) PUT state 409 —— 故意复用过期 baseRevision=0
curl -sS -i -X PUT "$BASE/api/v1/state" -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' --data-binary @/tmp/smoke-payload.json
# 期望 409 {"ok":false,"error":{"code":"revision_conflict"},"data":…,"revision":…,"updatedAt":…}

# (8) 登录限速 —— 连续 6 次错误密码，第 6 次期望 429（放最后：会锁该账号 15 分钟）
for i in 1 2 3 4 5 6; do
  curl -sS -o /dev/null -w "%{http_code}\n" -X POST "$BASE/api/v1/auth/login" \
    -H 'content-type: application/json' \
    -d '{"username":"<家长用户名>","password":"wrong-password"}'
done
# 期望输出：401 401 401 401 401 429；15 分钟后正确密码应恢复 200
```

全部通过后，在 postgres 侧复核 `family_state` 行形状（family_id/data/revision/updated_at）与 `family_state_history` 槽位已滚动（【归档】发布时，§4 C5/D14）。

### 5.10 注册家长账号与真机绑定

1. 家长在手机浏览器打开 `https://<your-domain>/` 完成注册/登录与首次引导（若 §5.9 已用 curl 注册正式账号，此步为登录）。
2. 孩子平板浏览器打开站点 → 家长输入一次账号密码登录 → 设备即完成「绑定」：此后凭 httpOnly refresh cookie 静默续期 access（30 天滚动），平板重开浏览器不再要求输密码。
3. 验证：平板重启浏览器后直接进入已同步状态；家长手机另行登录后两设备 revision 收敛一致（§4 D12）。

## 6. 回滚预案

回滚顺序原则（平移 v1）：**先 API 契约层、后静态、数据最后**；任何数据回退动作之前，**先 `pg_dump` 导出当前库留档**，再操作——孩子的真实学习记录不可逆。

### 6.1 前端回退（dist 版本化目录）

```bash
cd /opt/xiaotao
ln -sfn releases/dist-<旧版本> frontend/current
docker compose exec nginx nginx -s reload
```

验证：`index.html` 引用的 assets 文件名与旧版本发布档案一致、全部 200（`base:'./'` 相对路径，无路径残留问题）。风险口径（平移 v1）：若回退跨了契约变更，必须同时回退 api；归档版本与旧版本**不可混跑**（§6.4 / 闸门 E2）。

### 6.2 api 回退（镜像 tag）

```bash
# .env 中 API_IMAGE 改回旧 tag，然后：
docker compose up -d api
curl -sS https://<your-domain>/api/v1/health   # 确认 version 字段回到旧 sha
```

契约兼容矩阵（平移 v1 口径）：`/api/v1` 契约自基线冻结，非归档版本间任意前后端组合可混跑；**归档版本的回退必须连设备一起回退或升级**，否则旧客户端推送抹 archive（有 400 防线拦截，但仍以 E2 闸门为准）。

### 6.3 数据库迁移回退（prisma migrate resolve 说明）

Prisma **没有自动 down 迁移**，回退纪律如下：

1. **首选不做**：迁移坚持加性变更（只加表/加列/加索引，不删不收窄），使「代码回退 + 新 schema 共存」成立，数据库不动。
2. **破坏性迁移**（删列/改类型）必须拆两次发布，且执行前先 `pg_dump` 全量备份（§7）。
3. **迁移记录修复**：`migrate deploy` 半途失败会在 `_prisma_migrations` 留下 failed 记录，处理：

```bash
docker compose run --rm api npx prisma migrate status

# 场景一：失败的迁移实际已完整落库（人工核对 SQL 后）——标记为已应用：
docker compose run --rm api npx prisma migrate resolve --applied <migration_name>

# 场景二：确认回退（已手工用 SQL 撤销该迁移的改动）——标记为未应用：
docker compose run --rm api npx prisma migrate resolve --rolled-back <migration_name>
```

`resolve` 只改迁移账本不执行 SQL——改动本身必须人工完成并核对，这是它与新库现状保持一致的唯一保证。

### 6.4 数据回退（双路，平移 v1 并适配 v2 端点）

**路 A：云端历史版（`family_state_history` 环形槽位）**——适合「当天/近日误操作覆盖」：

1. `GET /api/v1/state/history`（Bearer）取 `{ items: [{revision, updatedAt}] }` 仅元数据列表，按时间选定目标版本；
2. `GET /api/v1/state/history/<revision>` 拉单份快照，存为 `restore-<日期>-r<revision>.json`（即 SyncState，schemaVersion=1）；
3. 任一设备「设置 → 导入备份」选择该文件（预览完成项/星星/桃粮 → 确认前自动导出当前快照 → 二次确认生效）；
4. 导入使本机 dirty，自动推送；若云端 revision 已前进触发 409 → 冲突弹窗选「保留这台平板的记录」→ 前端对齐修订号再推送，落库收敛。全程无人工 SQL 写操作，revision 只前进不倒退（刻意不提供「云端一键回滚」，避免破坏 CAS 单调性——02 §6.3）。

**路 B：家长 JSON 备份**——适合历史窗口之外（周级）或服务器整体不可用时：与路 A 第 3 步起完全相同，文件来源换 §7 的每周日导出。两路汇合于同一条既有导入链路，无需新增代码。

## 7. 备份与恢复

### 7.1 三层备份体系（v1 双路平移 + v2 新增 pg_dump）

| 层 | 机制 | 节奏/保留 | 依赖 |
|---|---|---|---|
| **pg_dump 全量（v2 新增，兜底之底）** | postgres 容器内每日导出（§7.2） | 每日 03:30；本地 7 天 + **异地 7 天**（对象存储/家长网盘） | cron（或 §7.3 备份容器） |
| 家长导出（主备份，平移 v1） | 设置页「导出备份」JSON | **每周日**晚固定导出；文件名 `小桃备份-YYYYMMDD.json`；至少两处存放（平板 + 家长手机/网盘） | 既有功能，零开发量 |
| 云端历史（近线兜底，平移 v1） | `family_state_history` 环形 10 槽 | 滚动覆盖约近日版本，不承诺跨周 | 02 §6.3 |

### 7.2 每日 pg_dump（主机 cron 方案）

```bash
# crontab -e（% 在 cron 中必须转义为 \%）
30 3 * * * cd /opt/xiaotao && docker compose exec -T postgres pg_dump -U xiaotao -d xiaotao | gzip > backups/pg/xiaotao-$(date +\%Y\%m\%d).sql.gz && find backups/pg -name 'xiaotao-*.sql.gz' -mtime +7 -delete

# 异地（建议）：用 rclone 同步到对象存储（阿里云 OSS / 腾讯 COS / 任意 S3 兼容）或家长网盘挂载目录，保留 7 天
50 3 * * * rclone copy /opt/xiaotao/backups/pg remote:xiaotao-backups --max-age 48h
```

### 7.3 备份容器替代方案（无主机 cron 时，如 NAS 部署）

在 compose 中追加（postgres 同镜像，零新增镜像）：

```yaml
  pg-backup:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      PGPASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - ./backups/pg:/backups
    entrypoint: ["/bin/sh", "-c"]
    command:
      - |
        while true; do
          pg_dump -h postgres -U xiaotao -d xiaotao -Z 9 \
            > /backups/xiaotao-$$(date +%Y%m%d-%H%M).sql.gz
          find /backups -name 'xiaotao-*.sql.gz' -mtime +7 -delete
          sleep 86400
        done
    depends_on:
      postgres:
        condition: service_healthy
    networks:
      - data
```

> 说明：循环自容器启动起算，不精确对齐时刻，家庭场景可接受；需要固定 03:30 用 §7.2 cron。异地同步仍需另配（NAS 一般自带云同步套件，可指向 `backups/pg/`）。

### 7.4 恢复步骤（灾难恢复）

```bash
cd /opt/xiaotao
docker compose stop api nginx
# 0. 若库还可连，先抢救性导出当前状态留档
docker compose exec -T postgres pg_dump -U xiaotao -d xiaotao | gzip > backups/pg/pre-restore-$(date +%Y%m%d%H%M).sql.gz
# 1. 重置数据卷（销毁现有数据，务必确认步骤 0 已留档）
docker compose down
docker volume rm xiaotao_postgres-data
# 2. 空库恢复
docker compose up -d postgres && docker compose ps postgres   # 等 (healthy)
gunzip -c backups/pg/xiaotao-YYYYMMDD.sql.gz | docker compose exec -T postgres psql -U xiaotao -d xiaotao
# 3. 起其余服务（api 入口脚本 migrate deploy 幂等核对 schema）
docker compose up -d
# 4. 验证：/health 200；家长登录 200；GET state 的 revision 与备份时点一致；
#    docker compose run --rm api npx prisma migrate status 无 failed
```

### 7.5 恢复演练（每季度一次）

在**同机第二套 compose 项目**（不动生产）上验证备份可用性：

```bash
cd /opt/xiaotao
docker compose -p xiaotao-restore up -d postgres    # -p 独立项目名 = 独立空卷/网络
gunzip -c backups/pg/$(ls backups/pg | tail -1) | docker compose -p xiaotao-restore exec -T postgres psql -U xiaotao -d xiaotao
docker compose -p xiaotao-restore exec postgres psql -U xiaotao -d xiaotao \
  -c 'select family_id, revision, updated_at from family_state;'
docker compose -p xiaotao-restore down              # 演练完拆除
```

通过标准：SQL 全量导入无报错；六表齐全；`family_state.revision` 与备份时点一致。演练记录（日期、备份文件名、结果）归档，与家长周日导出同季安排。

## 8. 监控与告警

### 8.1 /api/v1/health 探测

| 方式 | 做法 | 说明 |
|---|---|---|
| 外部免费拨测（推荐） | UptimeRobot 免费档（5 分钟间隔）监控 `https://<your-domain>/api/v1/health`，连续失败邮件告警到家长邮箱；或 healthchecks.io 类「心跳」服务由服务器 cron 定时 ping | 站点从公网侧探测，能发现服务器宕机/证书问题/503 降级（`db: down`） |

健康语义：200 `status:ok` 健康；503 `degraded/db:down` = api 活着但数据库故障（查 postgres 容器与磁盘）；超时/无法连接 = 服务器或网络故障。

### 8.2 pino 日志轮转与留存

- 全部容器统一 `json-file` 驱动 + `max-size: 10m` / `max-file: 3`（§3.2 已配）——每容器约 30MB 环形覆盖，无需独立日志系统。
- 启动即验证 redact（§4 D11）：日志中不得出现 Bearer token、cookie、`set-cookie` 值。
- 留存口径：容器日志仅服务近期排障；长期审计事实查 `security_events` 表（库内、随 pg_dump 备份），不依赖容器日志。

### 8.3 同步失败观测

- **security_events 表**（02 §3.4）：PIN 重置（pin-reset）、内容迁移（content-migrated）、refresh 复用检测（refresh-reuse）等已上云；前端本地环形 20 条照旧双写，离线可见。
- **sync 失败事件（思路，随 P1 排期）**：前端仿 `recordSecurityEvent` 增加失败事件环形记录与 best-effort 上报（仅记失败不记成功，`revision_conflict` 因有弹窗流程可不记），家长区「最近同步异常」一栏展示——家长报障时截图即可远程定位，比翻 DevTools 门槛低（v1 §7.2 建议平移）。
- **server 侧周查询**：

```sql
select type, count(*) from security_events
where created_at > now() - interval '7 days' group by type order by 2 desc;
```

出现 `refresh-reuse` 一律按疑似泄漏处置（该账号全部 refresh 已被自动吊销，家长重新登录即可，但要排查设备）；429 计数激增说明有人在撞密码。

### 8.4 周检清单（每周日晚，与家长导出同一时刻，约 10 分钟）

## 10. 密钥与配置管理

### 10.1 清单与红线

| 密钥/变量 | 存放 | 注入方式 | 禁止事项 |
|---|---|---|---|
| `POSTGRES_PASSWORD` | 服务器 `.env`（600） | compose 环境变量插值 → 两容器 | 四不入；仅初始化数据卷生效，改密走 §10.2 |
| `JWT_SECRET`（及可选 `ACCESS_TOKEN_SECRET`） | 同上 | 同上 → api 容器 | 四不入：不入 git（仓库只有 `.env.example` 键名）、不入前端 dist（§4 A8 扫描）、不入日志（redact）、不硬编码 |
| `DATABASE_URL` | compose 内由口令拼装 | api 容器环境变量 | 同上；连接串含口令，同等敏感 |
| 家长账号密码 | 家长记忆/密码本 | 登录时经 TLS 提交，库存 argon2id 哈希 | 服务端永不存明文；日志/备份只见哈希 |
| refresh cookie | 浏览器 httpOnly cookie | `Path=/api/v1/auth; Secure; SameSite=Strict` | JS 不可读；服务端只存 SHA-256 哈希（02 §2.3-4） |

### 10.2 生成与轮换流程

生成（上线即 §3.5）：

```bash
openssl rand -hex 32   # JWT_SECRET / ACCESS_TOKEN_SECRET（≥32 字节随机）
openssl rand -hex 24   # POSTGRES_PASSWORD
```

轮换：

1. **`JWT_SECRET`**（怀疑泄露时）：`.env` 换新值 → `docker compose up -d api`。代价与兼容策略——按 02 基线，全部 access token 立即失效（在线设备凭 refresh cookie 静默续期一次即恢复，影响分钟级）；refresh 为不透明随机串、库存哈希，**不受影响**。若同时怀疑 refresh 泄漏需彻底轮换：`update refresh_tokens set revoked_at = now();` 全量吊销——所有设备须重新输入密码登录，**「旧 refresh 失效」这一代价可接受，但须提前通知家长**择时操作，且操作前先 pg_dump。
2. **`POSTGRES_PASSWORD`**：改 `.env` 不生效（仅建卷时用），正确流程：

```bash
docker compose exec postgres psql -U xiaotao -d xiaotao \
  -c "alter user xiaotao with password '<新口令>';"
# 再更新 .env 中 POSTGRES_PASSWORD，然后：
docker compose up -d api        # 以新口令重连
```

### 10.3 本地开发替代（v1 假库链路退役）

- v1 的 `dev/fake-db.mjs` / `dev/function-preview.mjs` 假库与假身份头随平台方案退役删除（02 §8.4）；本地与 CI 一律用**真实 PostgreSQL**：`server/docker-compose.test.yml` 一键起 `xiaotao_test` 测试库，`beforeAll` 跑 `migrate deploy`、`afterEach` truncate 六表，supertest 驱动真实 Fastify 实例。
- 前端本地：`vite dev` 开发服务器代理 `/api` → 本地 api（或干脆不起 api——离线优先机制下前端可独立运行，同步横幅呈离线/未登录态，属预期）。
- **本地绝不使用生产 secret**：本地 `.env` 用随手生成的开发值（`openssl rand` 重新生成即可），与生产值永不相同；生产 secret 永不出现在开发机仓库副本。

## 附：发布最大风险备忘（v2 部署形态）

新形态的最大风险是「**无平台兜底的责任集中**」：TLS、限速、鉴权、补丁、备份全部压在家长自管的一台单机上，任一环节失守（强口令撞库未被限速拦住、postgres 意外映射端口、服务器宕机且异地备份缺失）都没有第二道墙。对应的最小纪律即 §4 的 B2/B6/B7/B8 与 §7 的异地备份——它们是闸门，不是建议项。归档升级窗口（RISK-01）仍是全流程中唯一「错了不可逆」的业务风险，E1/E2 两道硬闸门不因架构更换而放松。
